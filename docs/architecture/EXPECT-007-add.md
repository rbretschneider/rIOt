## 1. Summary

The agent reports the dpkg-wait step of a standalone `reboot` or `shutdown` through a wait reporter that the two handlers attach to the gate's context. The gate calls it once, at the first "held" observation, and the step is written on its own goroutine, so the gate never waits for it. The step that ends the wait is queued only after the power action has started. The server shows the "(waiting for dpkg lock)" suffix only while the device is online. That is a one-condition change in `expect/activity.go`, and the web label code is unchanged.

`agent_update_started`, `_completed` and `_failed` gain `from_version`, `to_version` and one correlation reference. On the command path the reference is the existing `command_id` field. On the self-update path it is a new `attempt_id` field, generated by the agent and persisted in the signed hand-off file. The field name is the kind, so the server never guesses the kind from the value. The server validates both as untrusted input:
- a command reference is checked against the device's own dispatched `agent_update` command;
- an attempt reference is matched inside the existing `CreateSelfUpdate` transaction, and the attempt ID is stored in the record's `params`.

Anything missing, invalid or unreadable falls back to EXPECT-002 behaviour.

Section G is built. The agent retries an update event at most 5 times within 90 seconds. Only the self-update start waits for delivery. The server stores a reference-linked event at most once per (device, linked command or record, type).

**No migration.** No change to `install.sh`, sudoers, the systemd unit, `riot-agent-apply`, `riot-apply-privileges`, the agent configuration schema or its collector whitelist.

## 3. Architecture Decisions

### AD-001: The dpkg-wait step is reported through a context-carried wait reporter; the gate signatures do not change

**Decision.**
- **New type.** `internal/agent/power_wait_step.go` defines `powerWaitReporter` (one per standalone power command) with the methods `enter()`, `settle()` and `leave()`. Two unexported context helpers carry it: `withPowerWaitReporter(ctx, r)` and `powerWaitReporterFrom(ctx)`.
- **The gate.** `awaitPowerClearance` gains one statement inside its existing `if !waiting { … }` block, after `waiting, firstHeld` are set and the Info line is written: `if r := powerWaitReporterFrom(ctx); r != nil { r.enter() }`. The block runs at most once per gate call, so FR-003 holds. A lock taken again after the guards passed never re-enters the block. A gate that finds the lock free or absent at its first check never enters it (FR-002).
- **The callers.** `handleReboot` and `handleShutdown` create the reporter and pass `withPowerWaitReporter(cr.ctx, rep)` as the gate's ctx. The post-patch callers (`commands.go:245`, `reboot_auth.go:239`) are not touched and never carry a reporter (FR-007, AC-009).
- **Unchanged.** `awaitPowerClearance`, `awaitRebootClearance` and `awaitShutdownClearance` keep their exact signatures and argument shapes.

**Rationale.**
- Every REBOOT-DPKG-001 and SHUTDOWN-DPKG-001 AST rule pins those signatures, and about 30 existing tests call them (NFR-014). A context value changes none of them.
- The `ctx` already flows to the gate's guards and sleeps. Only the two handlers that own a `cmdRun` can create a reporter.

**Alternatives considered.**
- *A new gate parameter or a `powerGate` field.* Rejected: it breaks AST rules 6 and 7 and every existing gate test.
- *An `Agent` field.* Rejected: it would be shared state across concurrent commands.
- *Polling the gate from the handler.* Rejected: it adds a second loop.

**Consequences.**
- A new AST test enforces the rule: `withPowerWaitReporter` is called only in `handleReboot` and `handleShutdown` (`TestEX7_AC009_OnlyStandaloneHandlersAttachWaitReporter`).
- The reporter cannot influence clearance. It has no return value and runs no guard.

### AD-002: The entering step never blocks the gate; the leaving step follows the power action; a skip fails in the wait step (Q-2)

**Decision.**

| Method | Called by | Behaviour |
|---|---|---|
| `enter()` | the gate, at most once | Sets `entered`. Starts one goroutine that runs `cr.Step(models.StepWaitDpkgLock)` and closes `done`. Returns at once. A second call is a no-op (`sync.Once`) |
| `settle()` | the handler, on every return path after the gate | If `entered`, waits for `done`. That is bounded by one local atomic write plus at most 1 s of notifier queue wait |
| `leave()` | the handler, **after** `execReboot`/`execShutdown` returned | If `entered`: `settle()`, then `cr.Step(models.StepPowerAction)` (new token `"power_action"`). No-op when the wait never began (FR-002 keeps today's behaviour exactly) |

**Handler order (reboot; shutdown is identical):**
1. Allow check.
2. `rep := newPowerWaitReporter(cr)`.
3. `c := a.awaitRebootClearance(withPowerWaitReporter(cr.ctx, rep), "reboot", cr.id, a.commonRebootGuards(""))`.
4. If `!c.Cleared`:
   - `rep.settle()`;
   - `res := rebootSkippedResult(c)`;
   - if `rep.entered()`, set `res.Step = models.StepWaitDpkgLock`;
   - return `res`. The message and reason are byte-for-byte today's (FR-005).
5. `err := a.execReboot(c.Permit)`. Nothing new runs between the gate's final probe and this call (REBOOT-DPKG-001 FR-012).
6. `rep.leave()`.
7. The result as today.

`completeCommand` then marks the last step `failed` for an error result, so the history shows `wait_dpkg_lock` failed (skip) or `wait_dpkg_lock` succeeded and `power_action` succeeded or failed (FR-010).

**Rationale.**
- `cr.Step` performs a durable write and can wait 1 s for queue space (Q-2). Running it on the gate's goroutine would delay the first re-poll, against FR-006.
- Queuing the leaving step before `execReboot` would insert that same work between the final probe and the power action, against FR-004 and REBOOT-DPKG-001 FR-012.
- After the power action has started, the only cost is a few milliseconds before `completeCommand` persists the result. For shutdown, the step follows `execShutdown`'s 3 s start check (`ShutdownStartCheckBound`).
- `settle()` before the skip result guarantees `cr.steps` already holds the wait step, so the failed step is the wait (FR-005).

**Alternatives considered.**
- *Synchronous `cr.Step` inside the gate.* Rejected: Q-2.
- *Leaving step before exec.* Rejected: FR-004.
- *No leaving step (the result alone).* Rejected: FR-004 requires one, and it matters while the result is still in flight.

**Consequences.**
- At most 2 step changes per command (AC-035).
- The goroutine is always joined before the handler returns, so no goroutine outlives its command.
- A failed exec after a wait now reports `failure_step = power_action`. Today that field is empty, and that stays so when no wait happened.
- The web gains the label "Waiting for dpkg lock" for `wait_dpkg_lock` and "Initiating" for `power_action` in `STEP_LABELS` (FR-010).

### AD-003: The waiting suffix is hidden server-side while the device is offline (FR-008, FR-009)

**Decision.** `expect/activity.go` `hostActivityLocked`: `WaitingDpkgLock: dev.online && w.cmd.Step == models.StepWaitDpkgLock`. Nothing else in `internal/server/expect/` changes. `web/src/utils/activity.ts` is unchanged.

**Rationale.**
- The tracker already knows `dev.online`, re-evaluates every second, and broadcasts `activity_update` only on change. A step change, a terminal state or an offline transition therefore clears the suffix within 1 to 2 s, well inside FR-009's 5 s.
- Doing it in the web would need a second rule there and would leave the API saying "waiting" for an offline device (BR-006).

**Alternatives considered.** A web-side check of `device_online`. Rejected: the truth would live in two places.

**Consequences.**
- One line in a file EXPECT-008 is unlikely to edit (EXPECT-008 edits `window.go`). This meets NFR-011.
- An old agent never reports the step, so the label stays "Rebooting" (AC-010).

### AD-004: Wire format of structured versions and references (Q-4)

**Decision.** `models.AgentEvent` gains three optional fields. All are `omitempty`, so an old agent's payload and the `agent_update_available` payload are byte-identical to today's (FR-037).

| JSON key | Go field | Meaning | Sent on |
|---|---|---|---|
| `from_version` | `FromVersion` | Agent version when the attempt started | the three update events, when known |
| `to_version` | `ToVersion` | Version the attempt installs | the three update events, when known |
| `command_id` | `CommandID` (existing) | **Command kind** reference | command-path update events only |
| `attempt_id` | `AttemptID` | **Attempt kind** reference | self-update-path update events only |

- **Kind rule.** The field name is the kind. When both `command_id` and `attempt_id` are non-empty, whatever their content, the event carries no reference (FR-027).
- **Agent side.** The agent never sets both. Versions are sent only as a pair: both non-empty, or both omitted.
- **Old servers.**
  - A v2.82+ server decodes these fields and ignores them, including `command_id` on these types (X-2).
  - Older servers' structs lack `attempt_id`, `from_version` and `to_version`, and encoding/json ignores them.
- **`ReceiveAgentEvent` keeps its decode line** (no `DisallowUnknownFields`).

**Rationale.**
- Reusing `command_id` matches the extra-updater precedent and the Docker-event precedent, and it is already the name of that concept everywhere.
- A separate `attempt_id` keeps the two kinds apart without a discriminator field.

**Alternatives considered.**
- *`ref_kind` plus `ref`.* Rejected: redundant, and it adds a third way to be inconsistent.
- *Inferring the kind from UUID shape.* Forbidden by FRD 7.1.

**Consequences.**
- `TestEX7_AC027_AgentEventJSONKeys` pins the exact key set per event and path.
- `TestEX7_AC027_NewPayloadDecodesIntoLegacyShape` decodes the new payloads into a frozen copy of the e120031 struct.

### AD-005: Attempt ID generation, persistence and recovery (FR-011, FR-013, FR-014, Q-8)

**Decision.**
1. **Generation.** `runUpdateCheck`, after the host lock is taken and before `started`:
   - `attempt := newUpdateAttempt(a.version, resp.LatestVersion)`;
   - the ID is `hex(16 bytes from crypto/rand)`: 32 lowercase hex characters, 128 bits, unpredictable;
   - a read error from `crypto/rand` makes the attempt carry **no** ID. The update still proceeds, and the server falls back to EXPECT-002.
2. **Propagation.** The attempt rides in `ctx` under a new key `updateAttemptKey{}`, next to the existing `updateCommandIDKey{}`.
3. **Persistence.** `performUpdate` reads both keys. `updateHandoff` gains `attempt_id`, `from_version` and `to_version` (all `omitempty`). They are filled **only when the command ID is empty**. They are saved by the existing `beforeApply → persistSignedHandoff`, which runs **before** `systemd-run` (FR-013), and passed in `onAccepted` to `watchSignedHandoff`.
4. **Use.**
   - `finishSignedHandoff`'s self-update branch sends `completed` or `failed` with `h.AttemptID`, `h.FromVersion` and `h.ToVersion`. That covers both the old process (helper `error`/`deferred`) and the restarted process via `recoverAutomaticSignedHandoff`.
   - It attaches the reference only if `h.AttemptID` passes `models.ValidRefToken`. It attaches the versions only if both are non-empty. Otherwise it sends neither (FR-014). It never substitutes `a.version`.
5. **Command path.** `handleTriggerUpdate` sends `CommandID = ctx.Value(updateCommandIDKey{})`, `FromVersion = a.version`, `ToVersion = resp.LatestVersion` on all three events, and never an attempt ID (FR-012). When the ctx carries no command ID (only in tests), it sends no reference.

**Rationale.**
- The hand-off file is already the agent-owned durable record of exactly this attempt. It is written before the helper launch and read by the restarted process. No new file, privilege or installer change is needed (NFR-006).

**Alternatives considered.**
- *A separate attempt file.* Rejected: a second file with the same lifecycle.
- *Deriving the ID from the digest.* Rejected: not unique per attempt (a retried identical release), and predictable.

**Consequences.**
- The hand-off file grows by at most 128 bytes, is still one file, and is overwritten per attempt (NFR-003).
- The first update **into** this release is finished by the new binary reading an old hand-off. It carries no reference (FR-014, AC-013).

### AD-006: Server attribution order with references (Section E)

**Decision.** `commands.AgentUpdateEventInput` gains the raw agent fields `CommandRef`, `AttemptRef`, `FromVersion` and `ToVersion`. The handler passes them only inside the existing authenticated-ID gate (FR-020). `NoteAgentUpdateEvent` validates them (AD-007, AD-011) and then proceeds:

**Step 1. Reference.** `ref := models.ParseAgentUpdateRef(in.CommandRef, in.AttemptRef)`, which yields `RefNone`, `RefCommand` or `RefAttempt`.

**Step 2. Command reference (FR-021, FR-022).**
- `s.repo.GetForDevice(ctx, ref.Value, deviceID)` (an existing, device-scoped PK read). It is valid only when all of these hold:
  - `Action == agent_update`;
  - `Origin != agent_self_update`;
  - `DispatchedAt != nil`;
  - the row is not terminal, or `FinishedAt >= at − 10m` (`models.SelfUpdateAttributionWindow`).
- **Valid** → return the link `{CommandID: C, CommandAttr: "agent", Dedupe: true}`. No record, no cap, no outcome change, for every type.
- **Not found, invalid, or read error** → continue as `RefNone`, with one Debug line that names no agent text. A read error is the NFR-008 fail-open case.

**Step 3. Attempt reference, `agent_update_started`.**
- Versions come from AD-007.
- `CreateSelfUpdate` receives `SelfUpdateStart{…, AttemptID: A}`. A new **step 0**, inside the existing transaction and after the advisory lock, selects the device's record whose `params->>'attempt_id' = A`, at any age and in any state.
  - **Found** → disposition `attempt_match` (new). The link is that record. Commit, with no cap count, no window change and no retire (FR-024).
  - **Not found** → the EXPECT-002 steps 1 to 5 run unchanged. A created row stores `attempt_id` (FR-023).
- `Dedupe = true` for `attempt_match` and `created`, because the link is to the record that owns A. For `attributed_command` and `open_record`, `Dedupe = false` (X-2 below).

**Step 4. Attempt reference, `agent_update_completed` / `_failed`.**
- `SelfUpdateByAttempt(device, A)` (new repo method).
  - **Found** → apply today's outcome logic (the refactored `applyRecordOutcome`, AD-004 of EXPECT-002) to that record, whatever its age (FR-025). Link with `"agent"` and `Dedupe = true`.
  - **Not found** → `LatestSelfUpdateSince(at − 10m)`. Use it only if `models.SelfUpdateAttemptID(rec) == ""` (FR-026), with link `"inferred"` and `Dedupe = false`. Otherwise there is no link.
  - **Read error** → process as `RefNone` (NFR-008).

**Step 5. No reference (FR-028).** Exactly today's `noteStart` / `noteOutcomeEvent`, except that a start's versions follow AD-007 (structured versions are independent of the reference).

**Rationale.**
- **Evidence first (BR-001).** Step 0 sits inside the transaction under the per-device lock, so concurrent replays of A can never create two records. A valid command reference short-circuits before any record logic, so a Ryan-pressed update can never touch a self-update record (S2, AC-021).
- **Device scope everywhere (BR-003).** `GetForDevice` and step 0 filter by `device_id`.

**Alternatives considered.**
- *Validating the command reference inside the `CreateSelfUpdate` transaction.* Rejected: it is needed for all three types, and only the start uses that transaction.
- *A separate attempt lookup before the transaction.* Rejected: race.

**Consequences.**
- `models.SelfUpdateDisposition` gains `attempt_match`.
- `SelfUpdateRepository` gains `SelfUpdateByAttempt`.
- The mock mirrors step 0, and a PG parity test covers it.

### AD-007: Structured versions on the server (FR-016 to FR-019; DEC-3 kept)

**Decision.**
- **Validation.** `models.StructuredSelfUpdateVersions(from, to) (string, string, bool)`: both must pass `ValidAgentVersion` (FRD 7.2, which is the EXPECT-002 grammar), and `!AgentVersionsMatch(from, to)`.
- **Start.** If the structured pair is valid, it is used for the record and every label. The message is **not** used for versions. If `ParseSelfUpdateStart(message)` also succeeds and gives a different pair, exactly one `Debug` line (`agent update start versions differ from the message`, `device_id` only) is written (FR-018). Otherwise `ParseSelfUpdateStart(message)` is used (FR-017), and if that fails, EXPECT-002 FR-003 applies.
- **Completed and failed.** Structured versions are ignored for state and attribution (FR-019). They are not validated, stored or shown.
- **Storage.** The agent's message is stored unchanged in every case.

**Rationale.**
- DEC-3 (a) is right on the code. Both values come from the same process, and treating a disagreement as unrecognised would turn a wording bug into offline pushes.
- Code review found no reason to change DEC-1, DEC-2 or DEC-4 either:
  - **DEC-1:** `riot-agent-apply` launch sites are only `applyStaged`.
  - **DEC-2:** see AD-010.
  - **DEC-4:** EXPECT-002 already nulls `dispatched_at` on revert, and AD-006 step 2 requires it.

### AD-008: The attempt ID lives in the record's `params`; no migration (Q-1)

**Decision.**
- `models.SelfUpdateParams(from, to, attemptID)`: the key `attempt_id` is added **only** when `attemptID != ""`. `attemptID` has already passed `ValidRefToken` (1 to 64 bytes of `[A-Za-z0-9-]`).
- `models.SelfUpdateAttemptID(c Command) string` re-validates on read.
- The lookup SQL is `… WHERE device_id=$1 AND origin='agent_self_update' AND params->>'attempt_id' = $2 ORDER BY created_at DESC LIMIT 1`. It uses the existing partial index `idx_commands_self_update_recent`, which holds at most 540 rows per device.

**Rationale.**
- The CHECK `commands_self_update_shape` does not constrain `params`, and the record is server-owned JSONB.
- A column or a unique index would need a migration that collides in time with EXPECT-008's 000035 (NFR-011).
- Uniqueness per (device, A) is guaranteed by step 0 under the advisory lock. Only `CreateSelfUpdate` inserts self-update rows.

**Alternatives considered.**
- *A column with a unique index.* Rejected: it needs a migration and gains nothing at ≤ 540 rows per device.
- *Storing A on the event.* Rejected: events have no such column.

**Consequences.**
- **No migration. No change to the origin set or any CHECK** (AC-039).
- The commands API returns `params.attempt_id` for self-update records. It is validated before storage (NFR-007), and the web does not render it.

### AD-009: De-duplication of reference-linked events (FR-035)

**Decision.**
- **Gate.** In `ReceiveAgentEvent`, after the link is computed and only when `link.Dedupe` is true, the handler takes the new `Handlers.agentUpdateEventMu`.
- **Check.** It calls the existing `h.events.HasCommandEvent(ctx, deviceID, link.CommandID, evt.Type)`.
  - `true` → `200 {"status":"duplicate"}`. Not stored, not broadcast.
  - `false` → store and broadcast as today, then release.
  - Read error → store anyway (NFR-008 forbids dropping), with one Debug line.
- **Unchanged.** `link.Events` (the rate-cap event) are broadcast as today. A repeat can never produce one, because `attempt_match` returns before the cap.

**Why every state effect of a repeat is already a no-op** (FR-035: no record, window, outcome or command change):
- a repeated start with A hits step 0;
- a repeated command-reference event is link-only;
- a repeated completed or failed event finds the record already terminal, so it is link-only (EXPECT-002 FR-022).

The dedupe therefore only guards storage and broadcast.

**Rationale.**
- It reuses the SEC-005 precedent and an existing indexed query. No new state.
- Keying on the **linked target** is exact only when the link came from the reference: a command reference names C itself, and an attempt match or creation is the one record that owns A. For timing-based links the key would merge distinct attempts, so they are not de-duplicated (X-2).

**Alternatives considered.**
- *A database unique index.* Rejected: it needs a migration and a column for the reference.
- *An in-memory seen-set.* Rejected: lost on restart (NFR-010), and it is per-event state.

**Consequences.**
- Single-process scope, as EXTRA-UPD-001 QA N-2 accepted (residual R-1).
- `command_attr = "agent"` (new constant `models.CommandAttrAgent`; the value already exists in Docker attribution) marks reference-linked rows. The EXPECT-002 events endpoint classifies `"agent"` as agent-sourced (its Section 6.3), so nothing changes there.

### AD-010: Bounded retry of update events on the agent (Section G built; DEC-2 kept; Q-7)

**Decision.** New file `internal/agent/update_events.go`:

- **Policy.** `models.UpdateEventMaxAttempts = 5`, `UpdateEventRetryBudget = 90s` (no attempt **starts** later than this after the first), `UpdateEventAttemptTimeout = 10s` (per-attempt context), and the schedule of attempt start offsets `0, 5s, 15s, 35s, 75s`. An attempt starts at `max(its offset, end of the previous attempt)`, provided that is ≤ 90 s after the first.
- **Classification (FR-031).**

  | Outcome | Action |
  |---|---|
  | Any 2xx | Accepted |
  | `*StatusError` with 5xx or 429 | Retry |
  | Any other `*StatusError` (other 4xx) | Stop. Debug |
  | `errNoServerClient` | Stop with no attempt, as today |
  | Any other error (transport, timeout, context deadline) | Retry |

  `HTTPClient.ReportEvent` now returns `c.newStatusError("event report", resp)` for status ≥ 400. That reads at most 4 KiB of body instead of an unbounded read.
- **Delivery modes.**

  | Mode | Used for | Behaviour |
  |---|---|---|
  | `deliverAwait` | self-update `agent_update_started` (FR-033) | All attempts in the caller's goroutine. `apply` runs after acceptance, a non-retryable answer, or budget exhaustion. The host lock stays held |
  | `deliverFirstSync` | self-update-path `completed` and `failed` (`runUpdateCheck`, `finishSignedHandoff`) | First attempt in the caller's goroutine, as today. Retries in one background goroutine. Keeps today's one synchronous attempt before `restart()` |
  | `deliverAsync` | all three command-path events (`handleTriggerUpdate`, FR-034) | Every attempt in one background goroutine. The command never waits |

- **Bound per process.** One retry slot per event type (three `atomic.Bool`). An event whose slot is busy gets exactly one attempt and no retries, so there are at most 3 retrying goroutines per process (NFR-003). A slot is released on acceptance, a non-retryable answer, or exhaustion. Background goroutines run on `a.commandContext()` and are counted in `a.cmdWG`.
- **Content.** Every attempt sends the same `*models.AgentEvent` value (FR-032).
- **Logs.** Debug per failed attempt. Exactly one Warn (`agent update event not delivered`, type and attempt count) when the budget is exhausted without acceptance (FR-036). Nothing is persisted.
- **Seams.**
  - The clock is `a.clock()` and the sleeper is `a.sleep` (`pause` seam).
  - The sink is `a.updateEventSink` (nil means `a.client.ReportEvent`).
  - The policy is `a.updateRetry *updateEventRetry`. **Nil means a single attempt** (today's behaviour). `Run()` sets `defaultUpdateEventRetry()`, so production always retries. The many existing tests that build `&Agent{}` with an `httptest` server keep exactly one attempt and never sleep (NFR-014).
- **Unchanged.** `agent_update_available` keeps `reportUpdateEvent`: one attempt, no fields (FR-037).

**Rationale.**
- The realistic loss is a release-day riot-server restart, which is well under 90 s (A-006). Only the start must survive it, because the restart kills the sender. A self-update has no deadline that 90 s could hurt (A-008).
- **Real risk assessment for deferral.** The only risk found is that an existing test could start sleeping for real. The nil-policy seam removes that risk, so Section G is **not deferred**.

**Alternatives considered.**
- *Retry without waiting (DEC-2 b).* Rejected: the self-update restart kills the retrier before the server is back.
- *A persisted outbox for events.* Rejected: unbounded state and more surface (NFR-003).

**Consequences.**
- A self-update can be delayed by at most 90 s + 10 s, and the command path not at all (NFR-004).
- On an old server, a retried event whose response was lost can be stored at most 5 times (NFR-013).

### AD-011: The agent's `command_id` on `agent_update_*` is now read, only under validation (supersedes EXPECT-002 X-2 narrowly)

**Decision.** The agent's `command_id` is read only:
- inside the existing authenticated-ID gate (`authenticatedDeviceID(r) == {id}`);
- only for the three update types;
- only when `attempt_id` is empty;
- only when it passes `ValidRefToken` and `IsCanonicalUUID`;
- and only as the input to `GetForDevice(id, device)` plus the four predicates of AD-006 step 2.

The only effect of a valid reference is the link `(C, "agent")` and the **absence** of self-update record logic. It never creates, extends or reopens a window, never changes C, and never changes any record.

**Rationale.**
- A device can only name its own command, so BR-003 holds.
- A valid reference reduces suppression (no record, no new window) and never adds any. A compromised agent gains nothing over EXPECT-002. It can already avoid creating a record by not sending a start.

**Consequences.**
- The EXPECT-002 QA gate item "ignores any agent `command_id`" is replaced by "reads it only under AD-011", which `TestEX7_AC023_*` and `TestEX7_AC029_*` test.
- The security researcher reviews this AD first.

### AD-014: Bounds (Ryan's standing rule: bounded growth and self-heal)

| Datum | New per device per day | Lifetime and cleanup |
|---|---|---|

## 7. Sequence / Flow

### 7.1 Reboot with a dpkg wait (AC-001, AC-002)

1. `handleReboot`: the allow check, then `rep` is created.
2. The gate's first probe sees the lock held:
   1. `firstHeld` is set and the Info line is written;
   2. `rep.enter()` starts goroutine G, which runs `cr.Step(wait_dpkg_lock)`: the step entry, `inflight.SetStep`, then `notifyProgress` queued;
   3. the gate sleeps 2 s at once.
3. The notifier sends progress `{state: running, step: wait_dpkg_lock}`. The server records the step, `CommandChanged` fires, and the next tick broadcasts "Rebooting (waiting for dpkg lock)" by ryan.
4. The lock is seen free, the guards run, and a fresh probe sees it free. `cleared()` mints the permit and the gate returns.
5. `execReboot(c.Permit)` starts the reboot. Nothing new ran between steps 4 and 5.
6. `rep.leave()`: join G, then `cr.Step(power_action)` is queued.
7. The result "reboot initiated after waiting 4m for the dpkg lock" goes to `completeCommand`, then `out.Add` (durable).
8. Server: the step change or the result clears the suffix within 1 to 2 s. If neither arrives before the host goes down, the device going offline clears it (AD-003).

### 7.2 Wait skipped (AC-003)

1. The gate returns `Skip = lock_timeout`.
2. `rep.settle()`.
3. The result is `failed` with today's message, and `Step = wait_dpkg_lock`.
4. The server stores the failed result with `failure_step = wait_dpkg_lock`. The window follows EXPECT-001 (device online, so no notification). The suffix clears on the terminal state.

### 7.3 Self-update (AC-011, AC-030)

1. `runUpdateCheck`: `available` (unchanged), host lock, then `attempt{ID: A, From, To}` is put in ctx.
2. `sendUpdateEvent(started, A, versions, deliverAwait)`: attempts until a 2xx, a non-retryable answer, or the budget.
3. Server: `ParseAgentUpdateRef`, which yields `RefAttempt`. Versions are structured if valid. `CreateSelfUpdate` runs the lock, step 0 (none found), then EXPECT-002 steps 1 to 5. The record is inserted with `params.attempt_id = A`. The link is `(R, agent, Dedupe)`. `HasCommandEvent(R, started)` returns false, so the event is stored and broadcast.
4. `apply`: `beforeApply` persists the hand-off (A, versions), then `systemd-run`. On `accepted`, `watchSignedHandoff` starts.
5. The helper restarts the agent. The restarted process registers (the record goes to `verifying`), then `recoverAutomaticSignedHandoff` loads the hand-off. On status `installed` with a digest match, it sends `completed(A, versions)` with `deliverFirstSync`.
6. Server: `SelfUpdateByAttempt(A)` finds R, which goes `verifying → succeeded`. The event is linked `(R, agent)` and stored once.

### 7.4 Ryan's "Update agents" (AC-020)

1. C is dispatched. `handleTriggerUpdate(ctx{C})` sends `started(command_id=C, versions)` with `deliverAsync`, then `performUpdate` at once.
2. Server: `RefCommand`. `GetForDevice(C, vermont)` passes (agent_update, user origin, dispatched, running). The link is `(C, agent)`. No record is created. The event is stored once.
3. The helper restarts the agent. The offline is covered by C's EXPECT-001 window (an info event linked to C). The re-registration closes the window 1 min later (PR #46). The restarted process completes C with a command result (unchanged).

### 7.5 Fail-open (AC-028)

A store read fails in `GetForDevice`, `SelfUpdateByAttempt` or step 0. The command and attempt lookups fall back to `RefNone`. A failing `CreateSelfUpdate` transaction gives an empty link (EXPECT-002 behaviour). The event is stored, the response is 200, and the offline alerts as under EXPECT-002 AC-020.

## 10. Security Considerations

| Vector | Mitigation |
|---|---|
| Agent names another device's command or record | Authenticated ID = `{id}` gate; `GetForDevice` and step 0 are device-scoped (AD-011, AC-029) |
| Agent names its own command to dodge records | Reduces suppression only. The window of C already exists. No record is created (AD-011) |
| Agent replays an attempt ID to reopen or extend suppression | Step 0 links only: no record, no cap count, no window change, even after close (AC-018) |
| Fresh attempt IDs per start to farm records | The EXPECT-002 cap of 6 per 24 h and its budget are unchanged (C-5) |
| Attempt completion of an old record (FR-025) | Transitions run only from `running`/`verifying` through `ActorSelfUpdate`. A terminal record is link-only. A completion can only shorten coverage, never past `hard` |
| Untrusted versions and references in labels | `ValidAgentVersion`, `ValidRefToken`, `IsCanonicalUUID`; re-validated on read; never logged as agent text |
| Retry flood | ≤ 5 attempts per event per 90 s per agent, under the ingest limit (2/s) |
| Duplicate storage race | In-process mutex around check and insert (single process, R-1) |
| Wait reporter abused to weaken the gate | It has no return value, mints nothing, and runs no guard. AST: only the two standalone handlers attach it. The permit, guard and signature rules are unchanged |
| Hand-off tampering by a local `riot`-user process | The file is agent-owned 0600. A tampered attempt only changes what this device reports about itself, validated as above |
| Real execution in tests | AD-015 scans (agent, server, web) |
