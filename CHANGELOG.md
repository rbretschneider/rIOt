## [Unreleased]

### Added

- [MAINT-RECOVERY-001] Independent signed apt maintenance worker with configure-first recovery, one bounded no-removal dependency repair, explicit `os_update` repair mode through the existing API, root-owned durable results and same-command recovery after agent restart. Repair preserves holds and never refreshes/upgrades/reboots. Existing apt security mode remains conservative upgrade behavior, not security-origin filtering.

### Maintenance deployment

- [MAINT-RECOVERY-001] Requires explicit root migration with a matching release containing both Linux helpers and the fixed unit; agent-only updates cannot grant or refresh privileged capabilities. Apt prerequisites are apt 2+, systemd 241+, sudo 1.9.10+, Python 3, and OpenSSL 3 or Python cryptography. No automatic apt/pip bootstrap. v2.72.0 lacks these assets. A real systemd PID 1 lifecycle smoke test remains required before production rollout; see [operator guide](docs/ops/os-maintenance.md).
- [MAINT-RECOVERY-001] Shared root exclusion blocks agent/apply/boot/installer replacement during active or unresolved maintenance; update acknowledgement is digest/time-bound rather than treating launch as success. Managed apt sudo policy uses one exact worker start and anchored package-name-only hold expressions, replacing direct apt/dpkg and unsafe wildcard hold grants. Installer authenticates assets and validates policy/units before replacement; doctor performs read-only checks. History stops new work at 32 terminal records or 16 MiB without automatic deletion. No API endpoint, UI, schema or runtime dependency change; DNF retains its existing inline behavior.

### Changed

- [APP-WORKSPACE-001] Unified Devices, Overview, Docker, monitoring and settings under one grouped application sidebar and compact search/notifications/account bar. Shared resource headers, global neutral surfaces and thin scrollbars keep the layout consistent; navigation collapses below 1280px. Devices retains every machine, while Docker hosts and filters exclude machines without Docker and keep offline Docker hosts. Existing URLs, authentication, stored/live logs, terminals and action confirmations are preserved.

### Security

- [AUTOUPD-HARDEN-001] **SEC-002:** Compose updates no longer run in a directory just because a container label names it. Before this change, the agent ran `docker compose` (root-equivalent) in the directory held by the `com.docker.compose.project.working_dir` label, so a container, or an image that defines that label, could point it at attacker-controlled files. Now, before every compose invocation, before it writes the sanitized compose copy and before it deletes a leftover one, the agent validates the directory and every file compose reads. The directory comes from the live compose project, not from the label alone. Every path component must be owned by root or an account that already has Docker rights, and writable by nobody else. Nothing may sit in the Docker data root or at or under a read-write mount of any container. The agent reads `.env` only for `COMPOSE_FILE` and `COMPOSE_PATH_SEPARATOR`. Compose runs with explicit `-f` files, a pinned `--project-name` and `DOCKER_HOST`, and no inherited `COMPOSE_*` variable. A refused update fails at `precheck` with `compose directory refused (<rule>)`, changes nothing, and counts as a failed run for the auto-update backoff. Every rule and its fix are in [Compose directory trust](README.md#compose-directory-trust), with the residual risks. **An agent stays unhardened until it is upgraded.** After upgrading, run `sudo -u riot riot-agent doctor` as the agent's service user.
- [GROWTH-001] **BREAKING for scripts:** state-changing requests (`POST`, `PUT`, `PATCH`, `DELETE`) that use the admin session cookie must now come from rIOt's own origin. This covers the dashboard API, `/api/v1/auth/*` and `/api/v1/setup/*`. A request passes when `Sec-Fetch-Site` is `same-origin`, or when `Origin` equals the origin it was made to or an entry in `RIOT_ALLOWED_ORIGINS`. Any other request gets `403` with `{"error":"origin_refused"}` before rIOt reads the body. A request with a body must also send `Content-Type: application/json`. The dashboard, `GET` requests and the agent endpoints are unaffected. Who must act: (1) Scripts that call the admin API without browser headers must send an `Origin` header equal to the URL they call, plus a JSON content type when they send a body. (2) Operators behind a TLS-terminating proxy should set `RIOT_TRUSTED_PROXIES`, and set `RIOT_ALLOWED_ORIGINS` to the public origin if the proxy rewrites or strips `Origin`. Entries match `Origin` exactly: `scheme://host[:port]`, no trailing slash. An unauthenticated cross-origin write now gets `403` where it used to get `401`. Refusals are logged at most once per client address per minute and never include header values. See [Origin check on state-changing requests](README.md#origin-check-on-state-changing-requests).
- [HARDEN-002] **BREAKING:** pprof is no longer served on the main listener. Before this change, `/debug/pprof` was mounted on the main port with no authentication, so anyone who could reach the server could read heap contents, goroutine stacks and command-line arguments. `/debug/pprof` and `/debug/pprof/*` now return `404` on the main port. Anyone who used `/debug/pprof` on the main port must switch to the new opt-in listener (see Added). See [Profiling (pprof)](README.md#profiling-pprof).
- [HARDEN-002] Every response now carries security headers: `Content-Security-Policy` (`default-src 'self'`, `script-src 'self'`, `form-action 'self'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`, and `connect-src` for same-host WebSockets), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`. The same-host `connect-src` value is built from the request `Host` only when it contains just letters, digits, `.`, `-`, `:`, `[` and `]`, so a crafted `Host` cannot inject CSP directives. `Strict-Transport-Security: max-age=31536000` is sent on HTTPS requests, decided by the same rule as the session cookie's `Secure` flag (direct TLS, or a trusted proxy sending `X-Forwarded-Proto: https`). HSTS applies to every port on the hostname and removes the browser's certificate-error click-through for a year; see [Security Headers](README.md#security-headers). **BREAKING:** the dashboard can no longer be embedded in an iframe. Embedded static assets now carry an explicit `Content-Type`.
- [HARDEN-002] Notification-channel secrets are write-only. The list, create and update responses of `/api/v1/settings/notification-channels` return `[rIOt-redacted]` in place of every secret (SMTP password, ntfy token and topic, Telegram bot token, Discord and Slack webhook URLs, Pushover keys, Gotify token, webhook URL and every webhook header value) and in place of credentials embedded in any channel URL (`https://user:pass@host`). A channel of an unknown type has every value redacted. A `PUT` that omits a secret or sends the placeholder keeps the stored value; a new value replaces it; `""` clears it. The placeholder is never stored. Secrets are also scrubbed from test-send errors, `notification_log.error_msg` and server logs. **BREAKING:** a client that read secrets from the API (for example to copy a channel to another server) now receives the placeholder. This does not protect against anyone who can edit channels, who can re-point a channel at a destination they control, and it does not protect secrets at rest. Rows written before this change may still contain leaked text until the 90-day notification-log retention removes them. See [Notification Channels](README.md#notification-channels).
- [HARDEN-002] The device registration key is now compared in constant time (SHA-256 digests of both values passed to `crypto/subtle.ConstantTimeCompare`). Accepted keys, rejected keys and the `401` response are unchanged.

### Removed

- [HARDEN-002] The unused notification retry queue (`internal/resilient/retry_queue.go`) and the README section that claimed failed notifications are retried automatically. Nothing used the queue; a failed notification is logged with status `failed` and is not retried. `internal/resilient` keeps the DNS cache and the HTTP client.

### Added

- [AUTOUPD-HARDEN-001] New agent setting `docker.compose_roots`, a list of absolute directories. When set, compose updates run only in a project directory inside one of them, and every `COMPOSE_FILE` entry must be inside one too. The setting is optional on Linux and required on Windows, where the agent cannot verify ownership; a Windows agent without it refuses every compose update with `windows_requires_roots`. An empty or relative entry refuses every compose update until it is fixed, and the rest of the agent keeps running. Restart the agent after changing it. The generated `agent.yaml` and the installer show it commented out.
- [AUTOUPD-HARDEN-001] `riot-agent doctor` runs the agent's compose trust rules against every Compose project directory on the host. It prints the `Compose roots` setting, a pass or fail line per project with the failing rule, the containers it ignores as compose sources, and any mount source compared through its readable prefix. It warns when it runs as a different user than the agent service, because root can read paths the agent cannot. Run it as `sudo -u riot riot-agent doctor`.
- [AUTOUPD-HARDEN-001] New `docker_update` parameter `compose_project`. The server and the dashboard name the compose project and the agent finds its directory among the live containers; `compose_work_dir` becomes a cross-check. An old server that sends only `compose_work_dir` still works with a new agent, which then looks up the project and applies every rule.

- [CMD-LIFECYCLE-001] Explicit command lifecycle. A command now moves through `queued`, `dispatched`, `acknowledged`, `running`, and `verifying` to a final state of `succeeded`, `failed`, `timed_out`, `cancelled`, or `expired`. One table in `internal/models/command_state.go` defines the allowed moves, and every database write is guarded by `UPDATE … WHERE status IN (…)`, so a late or duplicate report cannot change a finished command. The dashboard follows each command by ID and shows its real state and current step (for example "Updating… Pulling image"). `timed_out` accepts exactly one late final result from the agent. See [Command Lifecycle](README.md#command-lifecycle) in the README.
- [CMD-LIFECYCLE-001] New endpoints: `GET /api/v1/devices/{id}/commands/{cid}`, `POST /api/v1/devices/{id}/commands/{cid}/cancel` (queued commands only), and `POST /api/v1/devices/{id}/commands/{cid}/report` (agent, device-key auth; the HTTP path for acknowledgements, progress, and final results). `GET /api/v1/devices/{id}/commands` gains `active=true` and `target_key` filters. Creating a command returns a `409` body with `existing_command_id` when the target already has a command in flight. Field-level detail is in [Command endpoints](README.md#command-endpoints).
- [CMD-LIFECYCLE-001] Queued TTLs and execution deadlines per action class (reboot and shutdown 15 min and 10 min; OS patch 30 min and 40 min; Docker update 60 min and 35 min; bulk Docker update 60 min and min(35 min × targets + 5 min, 6 h); agent update 60 min and 15 min; everything else 30 min and 15 min). A sweeper runs at server start and every 60 seconds. It moves overdue queued commands to `expired` and overdue in-flight commands to `timed_out`. The delivery claim also checks the expiry, so an expired reboot is never delivered. Auto-dispatched commands under a `window` maintenance window expire no later than the window end.
- [CMD-LIFECYCLE-001] Cancel button for queued commands in the container and Compose stack views. Cancel and delivery are mutually exclusive: exactly one wins a race, and a cancel after dispatch returns `409`.
- [CMD-LIFECYCLE-001] One in-flight command per device and target (the host, a Compose project, or a container name). A bulk Docker update skips conflicting targets and reports each one in `conflicts`. The fleet bulk-update and bulk-patch responses gain a `conflicts` count.
- [CMD-LIFECYCLE-001] Agent result outbox. The agent writes each final result to `command-outbox.json` before it tries to deliver it, sends it over the WebSocket when connected, and falls back to the HTTP report endpoint with 5 s doubling backoff capped at 5 min. The outbox holds at most 200 entries and 1 MiB and drops entries older than 24 hours. If the server returns `404` or `405` without an error code, the agent switches to WebSocket-only legacy mode for one hour. Entries survive an agent restart.
- [CMD-LIFECYCLE-001] New agent state files in the agent data directory (`/var/lib/riot/`, or `%PROGRAMDATA%\riot\` on Windows), written with mode `0600`: `command-outbox.json`, `seen-commands.json` (command IDs already accepted, 1000 entries, 48 hours, so no command runs twice), and `inflight-commands.json` (one marker per running command, used to reconcile after a crash). No new privilege, sudoers rule, collector, or `collector.enabled` change is needed.
- [CMD-LIFECYCLE-001] New agent-to-server WebSocket messages `command_ack` and `command_progress`, and a server-to-agent `command_receipt` after each `command_result`. The final `command_result` keeps `status` of `success` or `error` and adds `step`, `outcome`, `stderr`, and `reason`. The dashboard WebSocket carries a new `command_update` message (see "Changed").
- [CMD-LIFECYCLE-001] Docker update safety on the agent. A standalone update renames the old container aside (`<name>.riot-old-<id8>`), creates and verifies the replacement, and removes the old container only after verification passes; on failure it rolls back and reports "rolled back to previous container". Network dependents that were running before an update are restored on every outcome. Compose pull and `up` have separate limits (15 min and 10 min). When a limit is reached, the agent sends SIGTERM and waits 60 s before SIGKILL. On startup, the agent reconciles a Docker update that a restart interrupted and reports it as `failed` with "agent restarted during execution; outcome unknown".
- [CMD-LIFECYCLE-001] Per-container update detection by running image ID. `ContainerInfo` gains `image_id`, `update_status` (`up_to_date`, `update_available`, `pinned`, `check_failed`), and `update_reason` (`registry_newer`, `pulled_not_recreated`). The "Update" badge's `title` states the reason. Container detail shows "Pinned by digest" and "Update check failed".
- [CMD-LIFECYCLE-001] The `telemetry` WebSocket message gains top-level `collected_at` and `received_at`, and `heartbeat` gains `received_at`. The dashboard drops any live telemetry at or before the latest `collected_at` it has applied for that device.
- [CMD-LIFECYCLE-001] Auto-update failure backoff. `auto_update_policies` gains `consecutive_failures` and `last_failure_at`. After a failed policy command, the policy waits min(15 min × 2^(n−1), 6 h) before it dispatches again.
- [CMD-LIFECYCLE-001] Migration `000023_command_lifecycle` (additive columns, status mapping, three partial indexes, and a working down migration). CI now runs a `postgres:16` service (pinned by digest, throwaway credentials, `permissions: contents: read`) so the PG-gated repository tests run on every pull request. Those tests read `RIOT_TEST_PG_URL` and skip unless the database name contains `test` or `RIOT_TEST_PG_ALLOW=1` is set.
- [CMD-LIFECYCLE-001] Per-device limits on agent reports: 120 per minute with a burst of 60, shared by HTTP and WebSocket; HTTP answers `429` and WebSocket drops the message. Identical or too-frequent progress reports are coalesced, and agent text is bounded and sanitized before it is stored.

- [UI-FOUNDATION-001] Toast notifications. Fleet bulk agent update, patch-all, and every device command (reboot, shutdown, patch, agent update, delete, and similar) now report their outcome in a toast at the bottom-right of the screen. Success and info toasts disappear after 5 seconds; hovering or focusing one pauses the timer. Error toasts stay until dismissed. At most four toasts show at once. Failures that used to be silent now raise an error toast. The previous inline success and error banners on the Fleet Overview and device pages are gone.
- [UI-FOUNDATION-001] Confirmation dialogs replace the browser's native `confirm()` and `alert()` everywhere in the dashboard. A dialog stays open with a spinner and disabled buttons while its action runs, shows a failure inline with the dialog still open so the user can retry or cancel, and closes with an optional success toast. Initial keyboard focus is always on **Cancel**, never on the confirm button, so a held Enter or key auto-repeat that opened the dialog cannot also confirm a destructive action. Escape and backdrop clicks are ignored while an action is running.
- [UI-FOUNDATION-001] Honest error states. When the Fleet Overview or a device page fails to load, it shows an error panel with the reason and a **Retry** button instead of "Add your first device" or "Device not found". "Device not found" now appears only for an HTTP 404. A fetch that is paused because the browser is offline shows the loading state, not an error. If a background refresh fails, the page keeps showing the last good data.
- [UI-FOUNDATION-001] UTC / local time switch. Click the clock in the header to switch every timestamp in the dashboard between UTC and the browser's local time. The default is UTC. The choice is stored in the browser's `localStorage` under `riot-time-zone`; any other stored value is ignored and UTC is used. Every absolute timestamp now carries a zone label (for example `2026-10-17 14:03:22 UTC`), and relative times ("5m ago") show the absolute time on hover. Chart axes and tooltips follow the same setting. Reboot-ETA and maintenance-window strings remain UTC regardless of the setting.
- [UI-FOUNDATION-001] Developer-facing design system under `web/src/components/ui`: design tokens (Tailwind utilities such as `bg-raised`, `text-text-muted`, `bg-danger`) and a single z-index scale defined in `web/src/index.css`, and the primitives `Button`, `Card`, `Badge`, `Modal`, `ConfirmDialog`, `EmptyState`, `Skeleton`, `QueryState`, `ToastProvider`/`useToast`, `RelativeTime` and `Timestamp`. Also: a typed `ApiError` in `web/src/api/errors.ts`, chart color constants in `web/src/theme/chartColors.ts`, and static guard tests that fail when the conventions are broken. See [web/src/components/ui/README.md](web/src/components/ui/README.md). No new dependency and no server change.
- [UI-FOUNDATION-001] Demo build: the demo API clients now implement every method of the real clients, enforced by the type checker, so the demo Dashboard shows populated charts, container leaderboard and activity, and no longer shows "WebSocket disconnected" or logs "No queryFn" errors on every page.
- [REG-HARDEN-001] Re-registering an existing device now requires proof that the caller is that device. `POST /api/v1/devices/register` accepts a request that names a known `device_id` only when it presents (a) that device's own API key in `X-rIOt-Key` (the record updates and no new key is issued), (b) a client certificate issued to that device that the TLS handshake verified against the rIOt CA and that is not revoked (the record updates and a new key is issued; existing keys stay valid), or (c) the registration key, and only for a device that has no API key at all (for example one created by mTLS enrollment; the key is issued once). A request that presents another device's key or certificate gets `403`. Anything else gets `401`. Every `401` and `403` from this endpoint now carries one of two fixed bodies, `{"error":"unauthorized"}` or `{"error":"forbidden"}`, identical whether or not the named device exists. A rejected request changes nothing: no record update, no key, no WebSocket broadcast, no device-online event. Each rejection is logged once at `WARN` (`device registration rejected`) with a sanitized device ID, client address, reason class, and status, and never with a key. New-device registration (no `device_id`, or an unknown one) is unchanged: open by default, or gated by the registration key in Settings when one is set, now compared in constant time. The request body is capped at 1 MiB (`400` above that). **Existing agents need no configuration change.** See [Device Registration and Re-registration](README.md#device-registration-and-re-registration) in the README.
- [REG-HARDEN-001] README recovery procedure for an agent that lost its API key but kept its device ID file: an admin rotates the key with `POST /api/v1/devices/{id}/rotate-key` and pastes it into `server.api_key` in `/etc/riot/agent.yaml`, then restarts the agent; or the operator deletes the device ID file (`/etc/riot/id`) so the agent registers as a new device, then deletes the stale device in the dashboard. A device enrolled with mTLS recovers on its own through its certificate. See [Recovering an agent that lost its API key](README.md#recovering-an-agent-that-lost-its-api-key).
- [REG-HARDEN-001] Future-dated telemetry is clamped. A heartbeat or telemetry snapshot whose timestamp is more than 5 minutes ahead of the server clock (`db.FutureSkewAllowance`) is stored with the server receive time instead, and the request still succeeds. Timestamps in the past, and timestamps up to 5 minutes ahead, are stored as sent. The server logs a clamp at most once per device and kind per hour, with the count of clamps since the previous line. All eight snapshot and heartbeat read queries also exclude stored rows dated more than 5 minutes ahead, so an already-stored future-dated row can no longer be a device's "latest" or appear in history. No row is rewritten or deleted and there is no migration. A device whose only rows are future-dated shows no data until it posts one fresh snapshot.
- [REG-HARDEN-001] Internal: new `DeviceRepository.HasAPIKey(ctx, deviceID)`; `HandlerDeps.CARepo` (wired only when mTLS is active); `internal/server/handlers/register_auth.go` holds the pure `decideReRegistration` decision; `internal/server/handlers/ingest_clamp.go` holds the timestamp clamp. A gated test (`TestTelemetryRepo_PGDisposable_*`, `TestDeviceRepo_PGDisposable_*`) runs against a disposable local PostgreSQL when `RIOT_QA_DISPOSABLE_DB_URL` is set and skips otherwise. No new dependency.

- [HARDEN-002] New `RIOT_PPROF_ADDR` environment variable (default empty, pprof off). Set it to a literal loopback `ip:port` (IPv4 in `127.0.0.0/8` or `::1`, port `1` to `65535`) to start a separate pprof listener. A hostname such as `localhost`, a non-loopback address, a malformed value, a port equal to `RIOT_PORT`, or a bind failure is logged at `ERROR` with the reason and leaves pprof off; none of them stops the server starting. A successful start logs a `WARN` with the bound address, and the listener shuts down with the server. In Docker, reach it with `docker exec riot-server wget -qO- http://127.0.0.1:<port>/debug/pprof/heap`. The compose files list the server environment explicitly, so add the variable to the `riot-server` `environment:` list.
- [HARDEN-002] New `GET /readyz` readiness endpoint. It returns `200` with `"status":"ready"` only when the database is reachable and schema migrations have completed in this process, otherwise `503` with `"status":"not_ready"`. The body is fixed (`status`, `database`, `migrations`, `time`) and carries no error text. It is public and is not blocked by the first-run setup guard.
- [REBOOT-ETA-001] Estimated-reboot-time hover tooltip on the Fleet Overview page. A device that is pending a reboot now shows, on hover, when that reboot is estimated to happen: the next start of the OS-patch maintenance window, as an absolute UTC time (for example `Est. reboot: 2026-10-19 02:00 UTC`). The tooltip appears in two places with byte-identical text: the existing **reboot required** badge in the Pending OS Patches panel, and a new small amber reboot glyph (`↻`) beside the pending-update count in the main device grid. Nothing already in the grid row was removed or changed. The text is always labelled an estimate, not a guarantee, and names what it depends on: reboot-class gating, the cooldown, and the device's `allow_reboot` / `hold_reboot_class` settings. It degrades honestly rather than inventing a time: window mode with no computable start, `disabled` mode, and no configured window show no time; `anytime` mode shows next-patch-run wording with no clock time; a device whose agent reports `allow_reboot: false` shows "Manual reboot required" with no time; a device whose agent does not report `allow_reboot` shows the time with the qualifier "if this device permits automatic reboot". See [Reboot ETA tooltip](README.md#reboot-eta-tooltip) in the README for the full matrix. No new dependency, no database migration, and no extra network request: both placements read the existing patch-status query.
- [REBOOT-ETA-001] `GET /api/v1/fleet/patch-status` gains four additive per-row fields, all `omitempty`: `os_patch_mode` (`window` / `anytime` / `disabled`), `next_window_start` (RFC 3339 UTC; present only in `window` mode when a start can be computed), `os_patch_cooldown_minutes` (present when non-zero), and `allow_reboot` (present only when the device's agent reports it). The response is still a top-level JSON array and existing fields are unchanged, so existing consumers are unaffected. The first three fields are server-wide and identical on every row; the server computes the next window start once per request.
- [REBOOT-ETA-001] The agent now reports its own `commands.allow_reboot` setting on the existing `updates` collector output (`UpdateInfo.allow_reboot`, a tri-state `*bool`: `true`, `false`, or absent for agents that predate this change). The value is display-only: no server dispatch, gating, or auto-patch decision reads it. It rides existing telemetry JSON storage, so no migration and no `collectors.enabled` change is needed. **Existing devices must upgrade their agent** to report it; until they do, the tooltip shows the conditional "if this device permits automatic reboot" wording instead of "Manual reboot required".
- [REBOOT-ETA-001] Internal: new pure server function `nextMaintenanceWindowStart(window, now)` in `internal/server/handlers/auto_update.go` returns the earliest eligible window start at or after `now` (UTC) and a found flag, honoring the `daily`, `weekly`, and `monthly` frequency rules and the existing overnight start-day convention, with the clock injected for testing. A `now` strictly inside an active window resolves to the next eligible occurrence; `now` exactly equal to a start returns that start. The search is bounded to 367 days. The web shared helper is `web/src/utils/rebootEta.ts` (`rebootEtaTooltip`, `formatUtc`).

- [AGENT-HARDEN-001] Signed releases. The release workflow now signs `checksums.txt` with an ed25519 key and publishes the detached signature as `checksums.txt.sig` (base64 of the 64-byte signature, one line) next to the binaries. The new `cmd/riot-signer` tool provides `genkey`, `sign`, and `verify`. The signing key is read only from the GitHub Actions secret `AGENT_SIGNING_PRIVATE_KEY`. After signing, the workflow runs `riot-signer verify` against the committed public key and fails the release if the signature does not verify or the committed key is invalid. **Maintainers must complete the one-time key setup in the README ("Releasing" section) before the next tag, or the release workflow fails.**
- [AGENT-HARDEN-001] New compile-time trust anchor: the agent embeds the ed25519 public key as `PublicKeyBase64` in `internal/releasekey/releasekey.go` (currently a placeholder until the maintainer commits the real key). It can be overridden at build time with `-ldflags -X github.com/DesyncTheThird/rIOt/internal/releasekey.PublicKeyBase64=<base64>`. No config file, environment variable, or server response can replace it.
- [AGENT-HARDEN-001] New root-owned update verifier `riot-agent-apply` (`cmd/riot-agent-apply`), installed by `install.sh` to `/usr/local/lib/riot/riot-agent-apply` (`root:root`, `0755`) and published per Linux platform as `riot-agent-apply-<platform>` (`linux-amd64`, `linux-386`, `linux-arm64`, `linux-armv7`, `linux-armv6`). It re-verifies the signature and SHA-256 over the exact bytes it installs, then writes them to `/usr/local/bin/riot-agent`. It rejects symlinked, non-regular, and oversized staged files. It is not auto-updated; re-run `install.sh` to refresh it.
- [AGENT-HARDEN-001] `signature_url` field (`omitempty`) on the `GET /api/v1/update/check` response, populated from the `checksums.txt.sig` release asset. It is a locator only; the server is not trusted to assert authenticity. The server also stops advertising a `riot-agent-apply-*` asset as the agent binary download.
- [AGENT-HARDEN-001] `riot-agent doctor` prints an **Agent Update** section on Linux when auto-update is enabled. It probes `sudo -n -l systemd-run --unit=riot-agent-update /usr/local/lib/riot/riot-agent-apply`, checks that the verifier exists with mode `0755`, and tells the operator to re-run the installer when either is missing.
- [AGENT-HEAL] The agent's `os_update` command now self-heals an interrupted `dpkg` state: on apt systems it runs `sudo dpkg --configure -a` between the package-index refresh and the upgrade. Previously, a `dpkg` transaction left half-configured by an earlier kill, reboot, or power-loss made apt refuse **every** subsequent run with `exit 100: E: dpkg was interrupted` — a one-time fault became a permanent nightly error until a human intervened. The repair is a fast no-op on a healthy system, and a repair failure is non-fatal (the upgrade still runs and reports the authoritative error). A new exact-match sudoers rule (`dpkg --configure -a`, installed by `scripts/install.sh`) backs it; **existing devices must re-run the install script to gain the rule** — until then the step is skipped. `riot-agent doctor` gains an "OS Update Self-Heal" check that probes for the rule and tells the operator to re-run the installer if it is missing.
- [PART-001] The six high-churn retention tables (`heartbeats`, `telemetry_snapshots`, `device_logs`, `container_metrics`, `container_logs`, `probe_results`) are now `PARTITION BY RANGE` on their timestamp column (`created_at` for `probe_results`), with retention enforced by **dropping aged-out partitions** instead of the previous hourly `DELETE` purge. A dropped partition returns disk space to the operating system immediately and generates zero dead tuples and zero autovacuum load — this is the permanent fix for the dead-tuple bloat described in `docs/ops/postgres-bloat.md` (e.g. `container_logs` reaching 28 GB against ~844 MB of live data). Retention **durations are unchanged**: 7 days for `heartbeats`/`container_logs`/`container_metrics`, `RIOT_RETENTION_DAYS` (default 30) for `telemetry_snapshots`/`device_logs`/`probe_results` — no new environment variable was introduced.
- [PART-001] The one-time conversion runs automatically on server startup through the existing embedded-migration path (`cmd/riot-server/migrations/000024`–`000028`). It is a metadata swap, not a data copy: the existing table is renamed and attached as a bounded "legacy" partition, so the O(rows) work (a composite-key index build and a bound-check validation) runs under non-blocking locks and the actual `ACCESS EXCLUSIVE` swap is sub-second and independent of table size — safe to run against a multi-gigabyte production database without taking the platform offline. The conversion is idempotent: re-running it on an already-converted table is a no-op, and recovering from an interrupted conversion (`migrate force` + reboot) requires no manual SQL.
- [PART-001] Every partitioned table also gets a near-empty forward `DEFAULT` catch partition, so a device with a skewed clock that pushes a future-dated row can never fail an insert or `COPY` batch for missing a partition — the row lands safely in the catch partition instead of the whole batch being rejected. A persistently non-zero row count in a catch partition is surfaced as a `WARN` log and via the manager's health snapshot, since it usually means one device's clock needs fixing.
- [PART-001] New hand-rolled Go partition manager (`internal/server/partition/`) pre-creates daily partitions three days ahead of need and drops partitions (including the legacy partition, once it fully ages out) on an hourly cycle. No `pg_partman`, no new PostgreSQL extension, and no new Go dependency were introduced. Partition create/drop actions are logged at `INFO`; genuine failures are isolated per table, logged at `ERROR`, and retried on the next cycle without stopping management of the other five tables.
- [PART-001] New `test-go-integration` CI job (`.github/workflows/ci.yml`) that runs the partitioning integration suite against a real, disposable PostgreSQL 16 service on every push/PR, including a hard gate that fails the build if the conversion ever rewrites data instead of performing a metadata-only swap.

### Changed

- [PART-001] The hourly retention worker (`runRetention`) no longer issues row-level `DELETE`s against the six tables above — drop-partition retention is now their sole retention mechanism. Retention for `events`, `notification_log`, server logs, device probe results, and stale bootstrap keys is unchanged. Because a partition is only dropped once its entire date range has aged out, effective retention on the six tables is now "at least the configured window" — up to one extra day of data may be retained beyond the exact window, a deliberate trade for O(1) drop-based retention.
- [PART-001] `docs/ops/postgres-bloat.md` Fix 3 (time-partitioning) is now shipped rather than a future recommendation; the interim per-table autovacuum tuning from migration `000023` is superseded for these six tables (a dropped partition generates no dead tuples, so there is nothing left for autovacuum to reclaim) but is left in place, since it still applies to the legacy partition until it ages out.

### Known Limitations

- [PART-001] The `.down.sql` migrations perform a best-effort reversal intended for dev/test rollback, not routine production use: pre-existing (legacy) rows are restored, but any rows written into the forward daily partitions or the catch partition after conversion are discarded. A production downgrade with meaningful post-conversion data requires a manual data-merge, which is not automated.
- [PART-001] This story does **not** reclaim bloat that already exists on disk from before the conversion — the legacy partition inherits the table's existing bloat and only shrinks when it fully ages out and is dropped. The one-time `VACUUM FULL` / `pg_repack` reclaim documented in `docs/ops/postgres-bloat.md` is still required for tables with existing bloat (`telemetry_snapshots` was still pending at time of writing).

- [OIDC-001] Optional "Sign in with SSO" OIDC login for the admin dashboard, alongside the existing password login (which is never removed or weakened). Dormant until `RIOT_OIDC_ISSUER_URL`, `RIOT_OIDC_CLIENT_ID`, and `RIOT_OIDC_CLIENT_SECRET` are all set; `RIOT_OIDC_BUTTON_LABEL` optionally overrides the button text (default `Sign in with SSO`). Uses Authorization Code + PKCE (S256) against a single OIDC issuer (e.g. authentik), discovered via the issuer's `.well-known` document. A successful callback mints the identical `riot_session` cookie a password login does — SSO is identity federation only; no IdP token is ever stored, and rIOt gains no user table, roles, or per-person permissions. See [Single Sign-On](README.md#single-sign-on-oidc) in the README for the enable-SSO runbook.
- [OIDC-001] New endpoints: `GET /api/v1/auth/oidc` (availability probe, answers `{"available": bool, "label": string}`, never `404`), `GET /api/v1/auth/oidc/start` (begins the login, redirects to the IdP), `GET /api/v1/auth/oidc/callback` (the IdP's return leg). `/start` and `/callback` are rate-limited per client IP (5/min, burst 5 — the same policy as password login, in a separate bucket so SSO flooding cannot lock out the password fallback) and respond `404` while SSO is dormant or while first-run setup is incomplete.
- [OIDC-001] New `external_identities` table (migration `000022`, additive, with a working rollback) recording one row per distinct (issuer, subject) that has signed in via SSO, with first-login/last-login timestamps and the asserted email. This is a pure audit record — nothing in the login path reads it to make an access decision. **Access control is delegated entirely to the identity provider's application-to-group binding**: any identity the IdP authenticates and authorizes for the rIOt application receives full rIOt admin, identical to a correct password. Binding the application to a specific group at the IdP is a required step, not optional hardening — see the README section.
- [OIDC-001] The first successful login from a previously unseen (issuer, subject) identity is logged at `WARN` level ("new SSO identity granted admin", with issuer/subject/IP) and is therefore persisted and visible in **Settings > Logs**. A repeat login from an already-seen identity logs at `INFO` only. This is the operator-facing signal for an authorization decision that rIOt itself does not make.
- [OIDC-001] New `RIOT_TRUSTED_PROXIES` environment variable (optional, default empty = trust nobody): a comma-separated list of CIDRs (bare IPs treated as `/32`/`/128`) trusted to supply `X-Forwarded-For` / `X-Real-IP` / `True-Client-IP` / `X-Forwarded-Proto`. Required for accurate per-client rate limiting, accurate audit IPs, and a `Secure` session cookie when rIOt runs behind a reverse proxy — see "Changed" below and the README.
- [GROWTH-001] Six optional `agent.yaml` keys bound what the agent keeps: `agent.buffer_max_mb` (default 50, range 5-64), `collectors.container_logs.max_lines` (50, 1-1000), `.max_bytes` (16384, 1024-262144) and `.max_line_bytes` (16384, 1024-16384), and `collectors.logs.max_entries_per_pass` (5000, 500-20000) and `.max_line_bytes` (4096, 1024-16384). An out-of-range integer is clamped and a non-integer falls back to the default, each with one warning. The agent still starts, and no existing config needs an edit. See [Agent Resource Bounds](README.md#agent-resource-bounds).
- [GROWTH-001] `riot-agent doctor` gains a **Collection Limits** section (the values in use after clamping) and, on Linux, a **Memory Limit** section that reports `MemoryMax` in bytes (`infinity` fails), `OOMPolicy`, `KillMode` and whether `GOMEMLIMIT` is set.
- [GROWTH-001] The agent removes its own staged update files older than one hour at start. `riot-agent-apply` removes its stale `.riot-agent.apply.<16 hex>` temp files (regular files older than one hour, in a directory owned by root and not writable by group or others) in both modes. The helper sweep needs an `install.sh` re-run on existing hosts.

### Fixed

- [GROWTH-001] The agent's offline buffer no longer grows without bound or blocks behind one bad item. It is capped by payload bytes (`agent.buffer_max_mb`, about that size plus SQLite overhead) and by 100 items, oldest dropped first with a warning. Each item leaves the buffer as soon as the server decides its fate, so an acknowledged item is never sent twice. The file shrinks after a flush. A buffer file from an older agent is converted once at the first start, and a failed conversion never stops the agent. A corrupt buffer is moved aside with its `-journal`, `-wal` and `-shm` files and replaced by an empty one.
- [GROWTH-001] A buffered or live telemetry item that the server rejects with a permanent 4xx (any 4xx except 401, 403, 408 and 429) is dropped with a warning instead of being retried forever. 401, 403, 408, 429 and 5xx keep the item. After a 429, 401 or 403 the agent sends no telemetry until `Retry-After` (clamped to 1 s-1 h) has passed, or for 30 s doubling to 10 min without the header. Heartbeats are unaffected.
- [GROWTH-001] A new agent on a full or read-only disk no longer registers a new ghost device on every restart. If a newly issued identity still cannot be saved, the agent logs the path and error, waits 60 s and exits with status 1.
- [GROWTH-001] A self-update download stops at 64 MiB: an oversize announced length is refused unread, and a longer stream is cut off. The partial file is deleted and `agent_update_failed` is reported.
- [GROWTH-001] A container that logged 50,000 lines in one interval, or a journal with a large backlog, no longer produces an unbounded read or an oversize push. A pass keeps at most 5,000 container lines and 4 MiB, the journal scan stops at 500,000 lines or 256 MiB, long lines are cut at a character boundary with a ` [truncated]` marker (also in `fetch_logs`), and a telemetry body over 6 MiB loses its container logs, then its journal entries. Authentication-failure counting still covers every journal line read.
- [CMD-LIFECYCLE-001] Per-container auto-update never ran. The server sent the container name while the agent required a container ID, so every run failed, and the failure started the cooldown. Symptom: container-level auto-update policies never updated anything and then stayed idle for the whole cooldown. The server now sends both the name and the ID, the agent resolves by name first (a leading `/` is ignored), and the cooldown starts only on success.
- [CMD-LIFECYCLE-001] The agent wrote to its WebSocket from several goroutines without a lock, and gorilla/websocket panics on concurrent writes. Symptom: the agent process crashed in the middle of a compose update. All writes are now serialized, a failed write returns an error to the caller, and the reconnect backoff resets after a successful connect (it used to stay at its maximum).
- [CMD-LIFECYCLE-001] Command results travelled only over the WebSocket, queued commands had no expiry, and nothing swept stuck rows. Symptoms: a command stayed on "sent" forever when the WebSocket dropped, and a queued reboot could fire days after it was requested. Results now go through a durable outbox with an HTTP fallback, every command gets a queued TTL and an execution deadline, and a sweeper resolves stale rows.
- [CMD-LIFECYCLE-001] Containers that share another container's network stack were stopped during an update and never restarted. Symptom: VPN clients and other sidecars stayed down after the parent updated. The agent now restores every dependent that was running, on every outcome, and fails the command at `restart_dependents` if one cannot be restored.
- [CMD-LIFECYCLE-001] A standalone update ignored pull errors and removed the old container before the new one existed. Symptom: a failed pull or create could leave the container deleted. The agent now fails on a pull error without touching the running container, renames the old container aside, and removes it only after the replacement passes verification.
- [CMD-LIFECYCLE-001] One 10-minute limit covered both compose pull and `up`, and reaching it sent SIGKILL. The `update_failed` event was then sent on the already-expired context. Symptoms: large pulls timed out midway, compose was killed in the middle of an operation, and the server never learned that the update failed. Pull and `up` now have separate limits, SIGTERM comes first with a 60-second grace period, and lifecycle events use a fresh 10-second budget.
- [CMD-LIFECYCLE-001] Update detection compared the registry with the local tag, not with the image the container runs. Failed registry checks were cached for 30 minutes, and any update wiped the whole cache. Symptoms: no "Update" badge for a container whose newer image was already pulled, failed checks that looked like "up to date", and a registry re-check for every image after each update. Detection now compares the running image ID, reports failed checks as `check_failed`, caches them for 5 minutes, and invalidates only the image references involved.
- [CMD-LIFECYCLE-001] There were no in-flight locks, heartbeat delivery could hand out a command that the WebSocket had already sent, and the cleanup of an old agent connection could remove the new one. Symptoms: the same command ran twice, two updates of one target raced each other, and after an agent reconnect the server could lose track of the live connection. The agent now holds a per-target lock and remembers command IDs, delivery uses one atomic claim, and the server removes a registration only if it still points at the closing connection.
- [CMD-LIFECYCLE-001] The dashboard applied older buffered telemetry after fresher telemetry, used the browser clock for timestamps and last-seen, and showed `exited` briefly during a recreate. Symptoms: tiles jumped back to older values, the last-seen time followed the browser clock, and a container flashed `exited` while it was being updated. The dashboard now drops stale messages by `collected_at`, takes last-seen from `received_at`, and shows "Updating…" while a tracked update is in flight.
- [CMD-LIFECYCLE-001] Any enrolled agent could apply a `command_result` to any command ID, because the WebSocket handler did not scope results to the sending device. All agent reports (acknowledgement, progress, and result, over WebSocket and HTTP) are now scoped to the authenticated device in the same SQL statement as the write, and a foreign or unknown command ID gets the same response as a missing one.
- [CMD-LIFECYCLE-001] The agent report endpoint now fails closed: a request that reaches it without a device authentication context is rejected with `401` instead of trusting the device ID in the URL.
- [CMD-LIFECYCLE-001] A telemetry snapshot with a timestamp far in the future could freeze a device's live state, because later real snapshots then looked stale. The server now orders snapshots by the REG-HARDEN-001 clamped timestamp (at most 5 minutes ahead of the receive time) and broadcasts that value as `collected_at`, and "latest" queries ignore rows further in the future.
- [CMD-LIFECYCLE-001] The `.compose.riot-sanitized.yml` file that the agent writes next to a compose file used a predictable name, followed symlinks, and had mode `0644`. The agent now creates it exclusively with mode `0600`, refuses to write over a symlink or a file it does not own, and removes it on every exit path and at startup.
- [CMD-LIFECYCLE-001] The command-completion event cut its reason at a fixed byte count, which could split a multi-byte character and produce invalid UTF-8, and a NUL byte in agent text could fail a database write. Agent text is now sanitized and cut on character boundaries, and a content problem no longer causes a server error.
- [CMD-LIFECYCLE-001] `terminal_output` and `terminal_close` messages from an agent socket were not tied to the device that owns the terminal session. Each session is now bound to its device, and a message from another device's socket is ignored.
- [UI-FOUNDATION-001] Patch-all on the Fleet Overview could dispatch twice if the confirm button was activated twice before the page re-rendered. It now has a synchronous in-flight guard and dispatches once.
- [UI-FOUNDATION-001] Device pages (device detail, device containers, container detail) showed "Device not found" while the browser was offline. They now show the loading state until the connection returns.
- [UI-FOUNDATION-001] Failed fetches on the Fleet Overview no longer show the first-run "Add your first device" guide. Failed bulk updates, patch-all and device commands no longer fail silently.
- [REG-HARDEN-001] A keyed agent's periodic re-registration no longer fails on a server that has a registration key. The agent re-registers every 24 hours and sends its own device key. The old gate at the top of `RegisterDevice` compared that header to the registration key and answered `401 invalid registration key`, so the refresh (hardware profile, version, tags) silently failed. The device's own key is now accepted on the re-registration path whether or not a registration key is set.
- [REG-HARDEN-001] A caller that knew only a device's ID could re-register that device, overwrite its hostname, tags, and hardware profile, and on a server with no registration key receive a new API key for it by sending no `X-rIOt-Key` header. This now requires the proof described above.
- [REG-HARDEN-001] The Fleet Overview table no longer renders a negative relative age (for example `-3m ago`) when an agent's clock is ahead of the browser's. A timestamp in the future now shows as `just now`. The Last Seen column renders `<RelativeTime pastOnly>`, whose `formatRelative(..., { pastOnly: true })` in `web/src/utils/format.ts` clamps the age at zero (merged with UI-FOUNDATION-001, which replaced the separate `formatAgo` helper).

- [AGENT-HARDEN-001] Agent auto-update no longer installs a binary it could not verify. Previously a checksum fetch failure only logged a warning, and an empty `checksum_url` skipped verification entirely, so a forged or compromised server could make every agent run attacker-chosen code as root. Every failure now refuses the update (see "Changed").
- [AGENT-HARDEN-001] `install.sh` no longer grants the `riot` user an arbitrary-root sudo primitive. The rules `systemd-run --unit=riot-agent-update sh -c *` and `sh -c mv -f ...` allowed any shell command as root; both are removed. A compromise of the unprivileged `riot` account is no longer a root compromise through the update path.
- [OIDC-001] The password-login rate limiter (`loginLimiter`, 5/min burst 5) could previously be bypassed entirely by an attacker supplying a spoofed `X-Forwarded-For` / `X-Real-IP` / `True-Client-IP` header, because the prior client-IP resolution (`chimw.RealIP`) trusted these headers unconditionally with no proxy configuration. The single shared admin password was therefore brute-forceable at CPU speed regardless of the rate limit. Client-IP resolution now trusts forwarding headers only from an explicitly configured `RIOT_TRUSTED_PROXIES` peer; see "Changed" for the operational consequence on proxied deployments.

- [GROWTH-001] **BREAKING for some manual installs:** the agent now writes `agent.yaml` atomically (temporary file beside it, fsync, rename), so it needs write access to the config directory, not only to the file. Installs made by `install.sh` are unaffected. A root-owned config directory, a symlinked `agent.yaml` (the rename replaces the link) or a single-file container bind mount (the rename fails) must be adjusted. Running package managers in their own transient unit is a follow-up (AGENT-PRIV). See [Memory limit](README.md#memory-limit).

The journal collector keeps the newest 5,000 entries per pass (it kept 500) and streams the journal instead of passing `-n 500` to `journalctl`.
- [GROWTH-001] A new agent proves it can write its identity before it registers, and a new agent on a read-only config directory waits in that pre-flight (retrying 5 s, doubling to 10 min) instead of registering. This is by design.
- [AUTOUPD-HARDEN-001] **BREAKING (upgrade note):** After an agent upgrade, a compose update that used to run can fail at `precheck` with `compose directory refused (<rule>)`. Nothing is stopped or recreated, and the failure feeds the normal auto-update backoff. Run `sudo -u riot riot-agent doctor` after upgrading and fix each failing project with the rule table in [Compose directory trust](README.md#compose-directory-trust). Also changed: the compose child no longer inherits `COMPOSE_*` or `DOCKER_CONTEXT` from the agent's environment (put `COMPOSE_PROFILES` and similar in the project's `.env`), compose loads exactly the validated files through explicit `-f` arguments, and it never walks up to a parent directory.
- [AUTOUPD-HARDEN-001] Server auto-update never skips a compose stack. It dispatches `compose_project` with `compose_work_dir`, or `compose_project` alone when the project's containers report more than one working directory (for example a symlinked stack directory after a partial recreate). The agent resolves symlinks. It updates the stack when the labels are one real directory and refuses with `ambiguous_project`, a failed command on the usual backoff, when they differ. A project-only command holds the target keys of every working directory the device reports, so a duplicate stays a conflict. An old agent receiving a project-only command fails it at `precheck` with "container, container_id or compose_work_dir is required" until it is upgraded; a new server still works with old agents in every other case.

- [CMD-LIFECYCLE-001] **BREAKING (API):** The `status` field of a command now holds one of ten canonical states: `queued`, `dispatched`, `acknowledged`, `running`, `verifying`, `succeeded`, `failed`, `timed_out`, `cancelled`, `expired`. The old values map as `pending` to `queued`, `sent` to `dispatched`, `success` to `succeeded`, and `error` to `failed`. Migration `000023` rewrites stored rows, and the API returns canonical values for any row. Integrations that match the old values must change. `GET /api/v1/devices/{id}/commands?status=` accepts both vocabularies and returns `400` for an unknown value.
- [CMD-LIFECYCLE-001] **BREAKING (WebSocket):** The dashboard WebSocket sends `command_update` once per accepted state change, and no longer sends `command_result`. Custom clients must listen for the new message. Final-result messages from agents keep `status` of `success` or `error`, so old agents and old servers keep working.
- [CMD-LIFECYCLE-001] `POST /api/v1/devices/{id}/commands` and `POST /api/v1/devices/{id}/docker/bulk-update` can now answer `409` when the target already has a command in flight. The bulk update returns `201` with a `conflicts` array when only some targets conflict.
- [CMD-LIFECYCLE-001] Auto-update cooldown now starts when a policy's command succeeds, not when it is dispatched. A failed, timed-out, expired, or cancelled command leaves the cooldown untouched and starts the failure backoff instead. A policy never dispatches while its own command is in flight.
- [CMD-LIFECYCLE-001] Heartbeat responses now contain only commands that the heartbeat itself claimed with an atomic `queued` to `dispatched` update. Queued commands past their `expires_at` are never delivered.
- [CMD-LIFECYCLE-001] A standalone `docker_update` whose pulled image ID equals the running container's image ID no longer recreates the container. It reports `succeeded` with "already up to date".
- [CMD-LIFECYCLE-001] Containers pinned by digest (`@sha256:` or a bare `sha256:` ID) are no longer checked against the registry and no longer report `update_available`. A failed registry check no longer reports `update_available: false`; it reports `update_status` of `check_failed`.
- [CMD-LIFECYCLE-001] A compose `docker_update` has a new `verify` step, reported as the `verifying` state. It checks that services that were running are running 10 seconds after `up`. Compose updates still have no rollback.
- [CMD-LIFECYCLE-001] On SIGTERM, the agent now waits up to 20 seconds for running commands, and rejects commands that arrive during shutdown. While a Docker update runs, the agent refuses `agent_update` and `agent_uninstall`, and the reverse.
- [CMD-LIFECYCLE-001] **Upgrade notes.** Upgrade the server first, then the agents. No `install.sh` re-run and no collector whitelist change is needed. Migration `000023` relabels historical rows silently: old `sent` rows become `timed_out`, overdue queued rows become `expired`, and the first sweep writes one `legacy commands relabelled` log line with no events or notifications. The migration also clears `last_triggered_at` on every container-level auto-update policy. Those policies never worked before, so they will fire for the first time in the next maintenance window. If another unmerged branch also adds a migration numbered `000023`, renumber the later one before deploying. Old agents keep their own bugs until upgraded. A new agent works against an old server in WebSocket-only legacy mode. See "Upgrade notes" in the [README](README.md#upgrade-notes).

- [UI-FOUNDATION-001] The header clock is now 24-hour and doubles as the UTC / local switch (see "Added"). The activity feed on the fleet dashboard shows relative times ("3d ago") with the absolute, zone-labelled time on hover, instead of a bare time of day.
- [UI-FOUNDATION-001] Hostnames render exactly as the agent reports them. The Fleet Overview, device pages, Alerts, Security, container pages and probe pages no longer force upper case.

### Known Limitations (v1)

- [CMD-LIFECYCLE-001] The telemetry staleness check and the snapshot insert are two separate database calls, not one transaction. If two snapshots from one device arrive at the same instant, both can be treated as the newest and both run the current-state side effects (primary IP update and similar). History stays correctly ordered, and a device posts telemetry sequentially, so the window is small.
- [CMD-LIFECYCLE-001] Only a `queued` command can be cancelled. The agent cannot interrupt a command after dispatch. Compose updates have no automatic rollback, and verification checks that a container is running 10 seconds after start, not its health check. A set-aside container left by a failed rollback blocks later updates of that container until someone renames it back or removes it by hand. TTLs, deadlines, step limits, and backoff are constants, not settings.
- [CMD-LIFECYCLE-001] If the heartbeat response that carries a claimed command is lost on the network, the command stays `dispatched` until its execution deadline and then becomes `timed_out`, although the agent never ran it. A `docker_update` that SIGTERM cuts off after the 20-second shutdown wait is reconciled at the next agent start, so the container can stay down until the agent is back.
- [CMD-LIFECYCLE-001] Deferred hardening items from the security review are tracked separately.
- [UI-FOUNDATION-001] A toast sits outside the modal dialog, so while a dialog is open a keyboard user cannot Tab to a toast's Dismiss button. The patch-all failure toast is raised while the review dialog is still open. A follow-up could show that error inline in the dialog. Other deferred work: the remaining un-migrated modals (SecurityScoreModal, CreateAlertDialog, DeviceProbeModal, ProbeModal, SetupGuide) and the wider sweep of raw `gray-*` classes outside `components/ui`.
- [UI-FOUNDATION-001] API error messages have the form `HTTP <status>: <statusText>`. Over HTTP/2, which a TLS reverse proxy usually negotiates, browsers report an empty `statusText`, so the text can read `HTTP 500: ` with a trailing colon.
- [REBOOT-ETA-001] The reboot-ETA tooltip is driven by `GET /api/v1/fleet/patch-status`, which lists only devices with at least one pending update. A device that needs a reboot but has zero pending updates (for example, after the packages were already applied) is not in that list, so it shows no reboot indicator or tooltip on the Fleet Overview page. The existing **Reboot Required** event and alert are unaffected.
- [REBOOT-ETA-001] The estimate uses the server-wide OS-patch window and the device's `allow_reboot` only. It does not see a device's `auto_patch` setting or whether `reboot_class` is `gated`, so for a device reporting `allow_reboot: true` in `window` mode the tooltip can show `Est. reboot:` without the "if" qualifier even when that device would not reboot automatically. The always-present caveat names these dependencies.
- [FLEET-DASH] The container leaderboard's "Restarts" sort uses a cumulative restart count rather than a true rolling 60-minute window. A follow-up story is needed to add rolling restart-count projection from historical telemetry.
- [FLEET-NET] Network throughput is host-summed only. Per-interface drilldown lives on the device detail page, not the fleet dashboard.
