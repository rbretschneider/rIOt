# Changelog

All notable changes to rIOt are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Versions correspond to git tags. See [Releases](https://github.com/rbretschneider/rIOt/releases) for binaries and full release notes.

## [Unreleased]

### Added

- [CMD-LIFECYCLE-001] Explicit command lifecycle. A command now moves through `queued`, `dispatched`, `acknowledged`, `running`, and `verifying` to a final state of `succeeded`, `failed`, `timed_out`, `cancelled`, or `expired`. One table in `internal/models/command_state.go` defines the allowed moves, and every database write is guarded by `UPDATE … WHERE status IN (…)`, so a late or duplicate report cannot change a finished command. The dashboard follows each command by ID and shows its real state and current step (for example "Updating… Pulling image"). `timed_out` accepts exactly one late final result from the agent. See [Command Lifecycle](README.md#command-lifecycle) in the README.
- [CMD-LIFECYCLE-001] New endpoints: `GET /api/v1/devices/{id}/commands/{cid}`, `POST /api/v1/devices/{id}/commands/{cid}/cancel` (queued commands only), and `POST /api/v1/devices/{id}/commands/{cid}/report` (agent, device-key auth; the HTTP path for acknowledgements, progress, and final results). `GET /api/v1/devices/{id}/commands` gains `active=true` and `target_key` filters. Creating a command returns a `409` body with `existing_command_id` when the target already has a command in flight. Field-level detail is in [Command endpoints](README.md#command-endpoints).
- [CMD-LIFECYCLE-001] Queued TTLs and execution deadlines per action class (reboot and shutdown 15 min and 10 min; OS patch 30 min and 40 min; Docker update 60 min and 35 min; bulk Docker update 60 min and min(35 min × targets + 5 min, 6 h); agent update 60 min and 15 min; everything else 30 min and 15 min). A sweeper runs at server start and every 60 seconds. It moves overdue queued commands to `expired` and overdue in-flight commands to `timed_out`. The delivery claim also checks the expiry, so an expired reboot is never delivered. Auto-dispatched commands under a `window` maintenance window expire no later than the window end.
- [CMD-LIFECYCLE-001] Cancel button for queued commands in the container and Compose stack views. Cancel and delivery are mutually exclusive: exactly one wins a race, and a cancel after dispatch returns `409`.
- [CMD-LIFECYCLE-001] One in-flight command per device and target (the host, a Compose project, or a container name). A bulk Docker update skips conflicting targets and reports each one in `conflicts`. The fleet bulk-update and bulk-patch responses gain a `conflicts` count.
- [CMD-LIFECYCLE-001] Agent result outbox. The agent writes each final result to `command-outbox.json` before it tries to deliver it, sends it over the WebSocket when connected, and falls back to the HTTP report endpoint with 5 s doubling backoff capped at 5 min. The outbox holds at most 200 entries and 1 MiB and drops entries older than 24 hours. If the server returns `404` or `405` without an error code, the agent switches to WebSocket-only legacy mode for one hour. Entries survive an agent restart.
- [CMD-LIFECYCLE-001] New agent state files in the agent data directory (`/var/lib/riot/`, or `%PROGRAMDATA%\riot\` on Windows), written with mode `0600`: `command-outbox.json`, `seen-commands.json` (command IDs already accepted, 1000 entries, 48 hours, so no command runs twice), and `inflight-commands.json` (one marker per running command, used to reconcile after a crash). No new privilege, sudoers rule, collector, or `collector.enabled` change is needed.
- [CMD-LIFECYCLE-001] New agent-to-server WebSocket messages `command_ack` and `command_progress`, and a server-to-agent `command_receipt` after each `command_result`. The final `command_result` keeps `status` of `success` or `error` and adds `step`, `outcome`, `stderr`, and `reason`. The dashboard WebSocket carries a new `command_update` message (see "Changed").
- [CMD-LIFECYCLE-001] Docker update safety on the agent. A standalone update renames the old container aside (`<name>.riot-old-<id8>`), creates and verifies the replacement, and removes the old container only after verification passes; on failure it rolls back and reports "rolled back to previous container". Network dependents that were running before an update are restored on every outcome. Compose pull and `up` have separate limits (15 min and 10 min). When a limit is reached, the agent sends SIGTERM and waits 60 s before SIGKILL. On startup, the agent reconciles a Docker update that a restart interrupted and reports it as `failed` with "agent restarted during execution; outcome unknown".
- [CMD-LIFECYCLE-001] Per-container update detection by running image ID. `ContainerInfo` gains `image_id`, `update_status` (`up_to_date`, `update_available`, `pinned`, `check_failed`), and `update_reason` (`registry_newer`, `pulled_not_recreated`). The "Update" badge's `title` states the reason. Container detail shows "Pinned by digest" and "Update check failed".
- [CMD-LIFECYCLE-001] The `telemetry` WebSocket message gains top-level `collected_at` and `received_at`, and `heartbeat` gains `received_at`. The dashboard drops any live telemetry at or before the latest `collected_at` it has applied for that device.
- [CMD-LIFECYCLE-001] Auto-update failure backoff. `auto_update_policies` gains `consecutive_failures` and `last_failure_at`. After a failed policy command, the policy waits min(15 min × 2^(n−1), 6 h) before it dispatches again.
- [CMD-LIFECYCLE-001] Migration `000023_command_lifecycle` (additive columns, status mapping, three partial indexes, and a working down migration). CI now runs a `postgres:16` service (pinned by digest, throwaway credentials, `permissions: contents: read`) so the PG-gated repository tests run on every pull request. Those tests read `RIOT_TEST_PG_URL` and skip unless the database name contains `test` or `RIOT_TEST_PG_ALLOW=1` is set.
- [CMD-LIFECYCLE-001] Per-device limits on agent reports: 120 per minute with a burst of 60, shared by HTTP and WebSocket; HTTP answers `429` and WebSocket drops the message. Identical or too-frequent progress reports are coalesced, and agent text is bounded and sanitized before it is stored.

- [REBOOT-ETA-001] Estimated-reboot-time hover tooltip on the Fleet Overview page. A device that is pending a reboot now shows, on hover, when that reboot is estimated to happen: the next start of the OS-patch maintenance window, as an absolute UTC time (for example `Est. reboot: 2026-10-19 02:00 UTC`). The tooltip appears in two places with byte-identical text: the existing **reboot required** badge in the Pending OS Patches panel, and a new small amber reboot glyph (`↻`) beside the pending-update count in the main device grid. Nothing already in the grid row was removed or changed. The text is always labelled an estimate, not a guarantee, and names what it depends on: reboot-class gating, the cooldown, and the device's `allow_reboot` / `hold_reboot_class` settings. It degrades honestly rather than inventing a time: window mode with no computable start, `disabled` mode, and no configured window show no time; `anytime` mode shows next-patch-run wording with no clock time; a device whose agent reports `allow_reboot: false` shows "Manual reboot required" with no time; a device whose agent does not report `allow_reboot` shows the time with the qualifier "if this device permits automatic reboot". See [Reboot ETA tooltip](README.md#reboot-eta-tooltip) in the README for the full matrix. No new dependency, no database migration, and no extra network request: both placements read the existing patch-status query.
- [REBOOT-ETA-001] `GET /api/v1/fleet/patch-status` gains four additive per-row fields, all `omitempty`: `os_patch_mode` (`window` / `anytime` / `disabled`), `next_window_start` (RFC 3339 UTC; present only in `window` mode when a start can be computed), `os_patch_cooldown_minutes` (present when non-zero), and `allow_reboot` (present only when the device's agent reports it). The response is still a top-level JSON array and existing fields are unchanged, so existing consumers are unaffected. The first three fields are server-wide and identical on every row; the server computes the next window start once per request.
- [REBOOT-ETA-001] The agent now reports its own `commands.allow_reboot` setting on the existing `updates` collector output (`UpdateInfo.allow_reboot`, a tri-state `*bool`: `true`, `false`, or absent for agents that predate this change). The value is display-only: no server dispatch, gating, or auto-patch decision reads it. It rides existing telemetry JSON storage, so no migration and no `collectors.enabled` change is needed. **Existing devices must upgrade their agent** to report it; until they do, the tooltip shows the conditional "if this device permits automatic reboot" wording instead of "Manual reboot required".
- [REBOOT-ETA-001] Internal: new pure server function `nextMaintenanceWindowStart(window, now)` in `internal/server/handlers/auto_update.go` returns the earliest eligible window start at or after `now` (UTC) and a found flag, honoring the `daily`, `weekly`, and `monthly` frequency rules and the existing overnight start-day convention, with the clock injected for testing. A `now` strictly inside an active window resolves to the next eligible occurrence; `now` exactly equal to a start returns that start. The search is bounded to 367 days. The web shared helper is `web/src/utils/rebootEta.ts` (`rebootEtaTooltip`, `formatUtc`).

- [AGENT-HARDEN-001] Signed releases. The release workflow now signs `checksums.txt` with an ed25519 key and publishes the detached signature as `checksums.txt.sig` (base64 of the 64-byte signature, one line) next to the binaries. The new `cmd/riot-signer` tool provides `genkey`, `sign`, and `verify`. The signing key is read only from the GitHub Actions secret `AGENT_SIGNING_PRIVATE_KEY`. After signing, the workflow runs `riot-signer verify` against the committed public key and fails the release if the signature does not verify or the committed key is invalid. **Maintainers must complete the one-time key setup in the README ("Releasing" section) before the next tag, or the release workflow fails.**
- [AGENT-HARDEN-001] New compile-time trust anchor: the agent embeds the ed25519 public key as `PublicKeyBase64` in `internal/releasekey/releasekey.go` (currently a placeholder until the maintainer commits the real key). It can be overridden at build time with `-ldflags -X github.com/DesyncTheThird/rIOt/internal/releasekey.PublicKeyBase64=<base64>`. No config file, environment variable, or server response can replace it.
- [AGENT-HARDEN-001] New root-owned update verifier `riot-agent-apply` (`cmd/riot-agent-apply`), installed by `install.sh` to `/usr/local/lib/riot/riot-agent-apply` (`root:root`, `0755`) and published per Linux platform as `riot-agent-apply-<platform>` (`linux-amd64`, `linux-386`, `linux-arm64`, `linux-armv7`, `linux-armv6`). It re-verifies the signature and SHA-256 over the exact bytes it installs, then writes them to `/usr/local/bin/riot-agent`. It rejects symlinked, non-regular, and oversized staged files. It is not auto-updated; re-run `install.sh` to refresh it.
- [AGENT-HARDEN-001] `signature_url` field (`omitempty`) on the `GET /api/v1/update/check` response, populated from the `checksums.txt.sig` release asset. It is a locator only; the server is not trusted to assert authenticity. The server also stops advertising a `riot-agent-apply-*` asset as the agent binary download.
- [AGENT-HARDEN-001] `riot-agent doctor` prints an **Agent Update** section on Linux when auto-update is enabled. It probes `sudo -n -l systemd-run --unit=riot-agent-update /usr/local/lib/riot/riot-agent-apply`, checks that the verifier exists with mode `0755`, and tells the operator to re-run the installer when either is missing.
- [AGENT-HEAL] The agent's `os_update` command now self-heals an interrupted `dpkg` state: on apt systems it runs `sudo dpkg --configure -a` between the package-index refresh and the upgrade. Previously, a `dpkg` transaction left half-configured by an earlier kill, reboot, or power-loss made apt refuse **every** subsequent run with `exit 100: E: dpkg was interrupted` — a one-time fault became a permanent nightly error until a human intervened. The repair is a fast no-op on a healthy system, and a repair failure is non-fatal (the upgrade still runs and reports the authoritative error). A new exact-match sudoers rule (`dpkg --configure -a`, installed by `scripts/install.sh`) backs it; **existing devices must re-run the install script to gain the rule** — until then the step is skipped. `riot-agent doctor` gains an "OS Update Self-Heal" check that probes for the rule and tells the operator to re-run the installer if it is missing.

- [OIDC-001] Optional "Sign in with SSO" OIDC login for the admin dashboard, alongside the existing password login (which is never removed or weakened). Dormant until `RIOT_OIDC_ISSUER_URL`, `RIOT_OIDC_CLIENT_ID`, and `RIOT_OIDC_CLIENT_SECRET` are all set; `RIOT_OIDC_BUTTON_LABEL` optionally overrides the button text (default `Sign in with SSO`). Uses Authorization Code + PKCE (S256) against a single OIDC issuer (e.g. authentik), discovered via the issuer's `.well-known` document. A successful callback mints the identical `riot_session` cookie a password login does — SSO is identity federation only; no IdP token is ever stored, and rIOt gains no user table, roles, or per-person permissions. See [Single Sign-On](README.md#single-sign-on-oidc) in the README for the enable-SSO runbook.
- [OIDC-001] New endpoints: `GET /api/v1/auth/oidc` (availability probe, answers `{"available": bool, "label": string}`, never `404`), `GET /api/v1/auth/oidc/start` (begins the login, redirects to the IdP), `GET /api/v1/auth/oidc/callback` (the IdP's return leg). `/start` and `/callback` are rate-limited per client IP (5/min, burst 5 — the same policy as password login, in a separate bucket so SSO flooding cannot lock out the password fallback) and respond `404` while SSO is dormant or while first-run setup is incomplete.
- [OIDC-001] New `external_identities` table (migration `000022`, additive, with a working rollback) recording one row per distinct (issuer, subject) that has signed in via SSO, with first-login/last-login timestamps and the asserted email. This is a pure audit record — nothing in the login path reads it to make an access decision. **Access control is delegated entirely to the identity provider's application-to-group binding**: any identity the IdP authenticates and authorizes for the rIOt application receives full rIOt admin, identical to a correct password. Binding the application to a specific group at the IdP is a required step, not optional hardening — see the README section.
- [OIDC-001] The first successful login from a previously unseen (issuer, subject) identity is logged at `WARN` level ("new SSO identity granted admin", with issuer/subject/IP) and is therefore persisted and visible in **Settings > Logs**. A repeat login from an already-seen identity logs at `INFO` only. This is the operator-facing signal for an authorization decision that rIOt itself does not make.
- [OIDC-001] New `RIOT_TRUSTED_PROXIES` environment variable (optional, default empty = trust nobody): a comma-separated list of CIDRs (bare IPs treated as `/32`/`/128`) trusted to supply `X-Forwarded-For` / `X-Real-IP` / `True-Client-IP` / `X-Forwarded-Proto`. Required for accurate per-client rate limiting, accurate audit IPs, and a `Secure` session cookie when rIOt runs behind a reverse proxy — see "Changed" below and the README.

### Fixed

- [CMD-LIFECYCLE-001] Per-container auto-update never ran. The server sent the container name while the agent required a container ID, so every run failed, and the failure started the cooldown. Symptom: container-level auto-update policies never updated anything and then stayed idle for the whole cooldown. The server now sends both the name and the ID, the agent resolves by name first (a leading `/` is ignored), and the cooldown starts only on success.
- [CMD-LIFECYCLE-001] The agent wrote to its WebSocket from several goroutines without a lock, and gorilla/websocket panics on concurrent writes. Symptom: the agent process crashed in the middle of a compose update. All writes are now serialized, a failed write returns an error to the caller, and the reconnect backoff resets after a successful connect (it used to stay at its maximum).
- [CMD-LIFECYCLE-001] Command results travelled only over the WebSocket, queued commands had no expiry, and nothing swept stuck rows. Symptoms: a command stayed on "sent" forever when the WebSocket dropped, and a queued reboot could fire days after it was requested. Results now go through a durable outbox with an HTTP fallback, every command gets a queued TTL and an execution deadline, and a sweeper resolves stale rows.
- [CMD-LIFECYCLE-001] Containers that share another container's network stack were stopped during an update and never restarted. Symptom: VPN clients and other sidecars stayed down after the parent updated. The agent now restores every dependent that was running, on every outcome, and fails the command at `restart_dependents` if one cannot be restored.
- [CMD-LIFECYCLE-001] A standalone update ignored pull errors and removed the old container before the new one existed. Symptom: a failed pull or create could leave the container deleted. The agent now fails on a pull error without touching the running container, renames the old container aside, and removes it only after the replacement passes verification.
- [CMD-LIFECYCLE-001] One 10-minute limit covered both compose pull and `up`, and reaching it sent SIGKILL. The `update_failed` event was then sent on the already-expired context. Symptoms: large pulls timed out midway, compose was killed in the middle of an operation, and the server never learned that the update failed. Pull and `up` now have separate limits, SIGTERM comes first with a 60-second grace period, and lifecycle events use a fresh 10-second budget.
- [CMD-LIFECYCLE-001] Update detection compared the registry with the local tag, not with the image the container runs. Failed registry checks were cached for 30 minutes, and any update wiped the whole cache. Symptoms: no "Update" badge for a container whose newer image was already pulled, failed checks that looked like "up to date", and a registry re-check for every image after each update. Detection now compares the running image ID, reports failed checks as `check_failed`, caches them for 5 minutes, and invalidates only the image references involved.
- [CMD-LIFECYCLE-001] There were no in-flight locks, heartbeat delivery could hand out a command that the WebSocket had already sent, and the cleanup of an old agent connection could remove the new one. Symptoms: the same command ran twice, two updates of one target raced each other, and after an agent reconnect the server could lose track of the live connection. The agent now holds a per-target lock and remembers command IDs, delivery uses one atomic claim, and the server removes a registration only if it still points at the closing connection.
- [CMD-LIFECYCLE-001] The dashboard applied older buffered telemetry after fresher telemetry, used the browser clock for timestamps and last-seen, and showed `exited` briefly during a recreate. Symptoms: tiles jumped back to older values, the last-seen time followed the browser clock, and a container flashed `exited` while it was being updated. The dashboard now drops stale messages by `collected_at`, takes last-seen from `received_at`, and shows "Updating…" while a tracked update is in flight.
- [CMD-LIFECYCLE-001] Any enrolled agent could apply a `command_result` to any command ID, because the WebSocket handler did not scope results to the sending device. All agent reports (acknowledgement, progress, and result, over WebSocket and HTTP) are now scoped to the authenticated device in the same SQL statement as the write, and a foreign or unknown command ID gets the same response as a missing one.
- [CMD-LIFECYCLE-001] The agent report endpoint now fails closed: a request that reaches it without a device authentication context is rejected with `401` instead of trusting the device ID in the URL.
- [CMD-LIFECYCLE-001] A telemetry snapshot with a timestamp far in the future could freeze a device's live state, because later real snapshots then looked stale. The server now clamps `collected_at` to at most 2 minutes ahead of the receive time, and "latest" queries ignore rows further in the future.
- [CMD-LIFECYCLE-001] The `.compose.riot-sanitized.yml` file that the agent writes next to a compose file used a predictable name, followed symlinks, and had mode `0644`. The agent now creates it exclusively with mode `0600`, refuses to write over a symlink or a file it does not own, and removes it on every exit path and at startup.
- [CMD-LIFECYCLE-001] The command-completion event cut its reason at a fixed byte count, which could split a multi-byte character and produce invalid UTF-8, and a NUL byte in agent text could fail a database write. Agent text is now sanitized and cut on character boundaries, and a content problem no longer causes a server error.
- [CMD-LIFECYCLE-001] `terminal_output` and `terminal_close` messages from an agent socket were not tied to the device that owns the terminal session. Each session is now bound to its device, and a message from another device's socket is ignored.

- [AGENT-HARDEN-001] Agent auto-update no longer installs a binary it could not verify. Previously a checksum fetch failure only logged a warning, and an empty `checksum_url` skipped verification entirely, so a forged or compromised server could make every agent run attacker-chosen code as root. Every failure now refuses the update (see "Changed").
- [AGENT-HARDEN-001] `install.sh` no longer grants the `riot` user an arbitrary-root sudo primitive. The rules `systemd-run --unit=riot-agent-update sh -c *` and `sh -c mv -f ...` allowed any shell command as root; both are removed. A compromise of the unprivileged `riot` account is no longer a root compromise through the update path.
- [OIDC-001] The password-login rate limiter (`loginLimiter`, 5/min burst 5) could previously be bypassed entirely by an attacker supplying a spoofed `X-Forwarded-For` / `X-Real-IP` / `True-Client-IP` header, because the prior client-IP resolution (`chimw.RealIP`) trusted these headers unconditionally with no proxy configuration. The single shared admin password was therefore brute-forceable at CPU speed regardless of the rate limit. Client-IP resolution now trusts forwarding headers only from an explicitly configured `RIOT_TRUSTED_PROXIES` peer; see "Changed" for the operational consequence on proxied deployments.

### Changed

- [CMD-LIFECYCLE-001] **BREAKING (API):** The `status` field of a command now holds one of ten canonical states: `queued`, `dispatched`, `acknowledged`, `running`, `verifying`, `succeeded`, `failed`, `timed_out`, `cancelled`, `expired`. The old values map as `pending` to `queued`, `sent` to `dispatched`, `success` to `succeeded`, and `error` to `failed`. Migration `000023` rewrites stored rows, and the API returns canonical values for any row. Integrations that match the old values must change. `GET /api/v1/devices/{id}/commands?status=` accepts both vocabularies and returns `400` for an unknown value.
- [CMD-LIFECYCLE-001] **BREAKING (WebSocket):** The dashboard WebSocket sends `command_update` once per accepted state change, and no longer sends `command_result`. Custom clients must listen for the new message. Final-result messages from agents keep `status` of `success` or `error`, so old agents and old servers keep working.
- [CMD-LIFECYCLE-001] `POST /api/v1/devices/{id}/commands` and `POST /api/v1/devices/{id}/docker/bulk-update` can now answer `409` when the target already has a command in flight. The bulk update returns `201` with a `conflicts` array when only some targets conflict.
- [CMD-LIFECYCLE-001] Auto-update cooldown now starts when a policy's command succeeds, not when it is dispatched. A failed, timed-out, expired, or cancelled command leaves the cooldown untouched and starts the failure backoff instead. A policy never dispatches while its own command is in flight.
- [CMD-LIFECYCLE-001] Heartbeat responses now contain only commands that the heartbeat itself claimed with an atomic `queued` to `dispatched` update. Queued commands past their `expires_at` are never delivered.
- [CMD-LIFECYCLE-001] A standalone `docker_update` whose pulled image ID equals the running container's image ID no longer recreates the container. It reports `succeeded` with "already up to date".
- [CMD-LIFECYCLE-001] Containers pinned by digest (`@sha256:` or a bare `sha256:` ID) are no longer checked against the registry and no longer report `update_available`. A failed registry check no longer reports `update_available: false`; it reports `update_status` of `check_failed`.
- [CMD-LIFECYCLE-001] A compose `docker_update` has a new `verify` step, reported as the `verifying` state. It checks that services that were running are running 10 seconds after `up`. Compose updates still have no rollback.
- [CMD-LIFECYCLE-001] On SIGTERM, the agent now waits up to 20 seconds for running commands, and rejects commands that arrive during shutdown. While a Docker update runs, the agent refuses `agent_update` and `agent_uninstall`, and the reverse.
- [CMD-LIFECYCLE-001] **Upgrade notes.** Upgrade the server first, then the agents. No `install.sh` re-run and no collector whitelist change is needed. Migration `000023` relabels historical rows silently: old `sent` rows become `timed_out`, overdue queued rows become `expired`, and the first sweep writes one `legacy commands relabelled` log line with no events or notifications. The migration also clears `last_triggered_at` on every container-level auto-update policy. Those policies never worked before, so they will fire for the first time in the next maintenance window. If another unmerged branch also adds a migration numbered `000023`, renumber the later one before deploying. Old agents keep their own bugs until upgraded. A new agent works against an old server in WebSocket-only legacy mode. See "Upgrade notes" in the [README](README.md#upgrade-notes).

- [AGENT-HARDEN-001] **BREAKING:** Agent auto-update is now cryptographically verified and fail-closed. The agent installs an update only if the ed25519 signature on `checksums.txt` verifies against its compiled-in public key and the binary's SHA-256 matches the signed entry. It refuses, keeps the current binary running, logs an error, and raises an `agent_update_failed` event on a missing or non-200 `checksums.txt` or `checksums.txt.sig`, an invalid signature, a missing or ambiguous checksum entry, a checksum mismatch, a timeout, or a body over 1 MiB. Auto-update stays on by default; `agent.auto_update: false` still disables it. **Operator-visible effect:** any release published without `checksums.txt.sig`, including every release before this change, is refused with one error event per 6-hour cycle. The first release built from this change is the first one hardened agents can install.
- [AGENT-HARDEN-001] **BREAKING:** The update sudoers rules changed. `install.sh` now writes exactly `systemd-run --unit=riot-agent-update /usr/local/lib/riot/riot-agent-apply` plus the existing `systemctl reset-failed riot-agent-update`, with no shell, no wildcard, and no arguments. The installed agent binary `/usr/local/bin/riot-agent` is now `root:root` (it was `riot:riot`), and the service unit's `ExecStartPre` runs `riot-agent-apply --boot` instead of an unverified `cp`. The package-manager, reboot, `smartctl`, and `nginx` rules are unchanged. **Existing hosts must re-run `install.sh`** to receive the verifier, the root-owned binary, the tightened rule, and the new unit. Until they do, the hardening is not in effect on that host, and `riot-agent doctor` reports the update sudo rule or verifier as missing. A re-run is also required after any change of the release signing key, because the verifier is not auto-updated.
- [AGENT-HARDEN-001] If a release does not publish `riot-agent-apply-<platform>` (for example when you install an old version with `--version`), `install.sh` prints a warning and continues. Automatic updates stay unavailable on that host until it is installed from a release that publishes the verifier.
- [AGENT-HARDEN-001] Best-effort downgrade guard: the agent ignores an update when the server's advertised `latest_version` is not strictly newer than the running version (a dashboard-triggered update returns an error instead). This is not full anti-rollback. The version is not part of the signed data, so a compromised server can still serve an older, genuinely signed release (recorded as a follow-up).
- [AGENT-HEAL] The agent's package-manager commands (refresh / dpkg-repair / upgrade) now terminate gracefully on the 30-minute timeout: instead of Go's default immediate `SIGKILL`, the agent sends `SIGTERM` (which `sudo` forwards to apt/dpkg so an in-flight transaction can finish or roll back) and only escalates to `SIGKILL` after a 90-second grace period. This keeps the agent itself from abandoning `dpkg` mid-configure on a slow host with a large batch. Other agent commands are unchanged.

- [OIDC-001] `riot_session`'s `SameSite` attribute changed from `Strict` to `Lax`, paired with a new scheme-derived `Secure` attribute (set whenever the resolved request scheme is `https`; omitted over plain HTTP so LAN/self-signed deployments are unaffected). `Lax` is required so the session survives the cross-site redirect that returns the browser from an SSO login; the paired `Secure` addition keeps the cookie from being sent over a cleartext `http://` request to the same host. Every mutating rIOt endpoint is `POST`/`PUT`/`DELETE`, so CSRF exposure is unchanged. Applies identically to password and SSO sessions — both are minted by one shared helper.

### Known Limitations (v1)

- [CMD-LIFECYCLE-001] The telemetry staleness check and the snapshot insert are two separate database calls, not one transaction. If two snapshots from one device arrive at the same instant, both can be treated as the newest and both run the current-state side effects (primary IP update and similar). History stays correctly ordered, and a device posts telemetry sequentially, so the window is small.
- [CMD-LIFECYCLE-001] Only a `queued` command can be cancelled. The agent cannot interrupt a command after dispatch. Compose updates have no automatic rollback, and verification checks that a container is running 10 seconds after start, not its health check. A set-aside container left by a failed rollback blocks later updates of that container until someone renames it back or removes it by hand. TTLs, deadlines, step limits, and backoff are constants, not settings.
- [CMD-LIFECYCLE-001] If the heartbeat response that carries a claimed command is lost on the network, the command stays `dispatched` until its execution deadline and then becomes `timed_out`, although the agent never ran it. A `docker_update` that SIGTERM cuts off after the 20-second shutdown wait is reconciled at the next agent start, so the container can stay down until the agent is back.
- [CMD-LIFECYCLE-001] Deferred hardening items from the security review are tracked separately.
- [REBOOT-ETA-001] The reboot-ETA tooltip is driven by `GET /api/v1/fleet/patch-status`, which lists only devices with at least one pending update. A device that needs a reboot but has zero pending updates (for example, after the packages were already applied) is not in that list, so it shows no reboot indicator or tooltip on the Fleet Overview page. The existing **Reboot Required** event and alert are unaffected.
- [REBOOT-ETA-001] The estimate uses the server-wide OS-patch window and the device's `allow_reboot` only. It does not see a device's `auto_patch` setting or whether `reboot_class` is `gated`, so for a device reporting `allow_reboot: true` in `window` mode the tooltip can show `Est. reboot:` without the "if" qualifier even when that device would not reboot automatically. The always-present caveat names these dependencies.
- [FLEET-DASH] The container leaderboard's "Restarts" sort uses a cumulative restart count rather than a true rolling 60-minute window. A follow-up story is needed to add rolling restart-count projection from historical telemetry.
- [FLEET-NET] Network throughput is host-summed only. Per-interface drilldown lives on the device detail page, not the fleet dashboard.
